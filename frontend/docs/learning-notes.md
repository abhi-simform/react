# ShopSphere learning notes

## 0.1 Tour the scaffold

One sentence per file:

- `app/root.tsx`: the HTML document shell (`Layout` with `Meta`/`Links`/`Scripts`), the root `<Outlet/>` and the global `ErrorBoundary`.
- `app/routes.ts`: the single source of truth for the route tree (`index`, `route`, `layout`, `prefix`), each entry points at a module under `app/routes/`.
- `app/routes/home.tsx`: the page module for `/`; its default export is the component rendered inside the root `<Outlet/>`.
- `app/app.css`: the Tailwind v4 entry plus the theme tokens (CSS variables) that shadcn components read.
- `app/components/ui/button.tsx`: a shadcn/base-ui `Button` primitive with `cva` variants; generated code, wrap it instead of editing per use.
- `app/lib/utils.ts`: exports `cn()` (class-name merging helper) used by every UI component.
- `vite.config.ts`: wires the Tailwind and React Router Vite plugins and turns on `tsconfigPaths` so the `@/` alias works in the bundler.
- `tsconfig.json`: strict TypeScript, bundler module resolution, `verbatimModuleSyntax`, and the `@/*` path alias to `./app/*`.

### View Source vs Elements (SPA mode)

`ssr: false` means the server (Vite dev / static host) sends an HTML shell with no page content: View Source (`curl localhost:5173`) shows a `<body>` containing only scripts and the `__reactRouterContext` bootstrap. The Elements panel shows the live DOM after React rendered in the browser. That difference is client-side rendering; the trade-off is a blank first paint until JS runs and weaker SEO for crawlers that do not run JS.

### Typo in `routes.ts`

I registered `route("hello", "routes/helo.tsx")` (typo) and Vite returned HTTP 500 with `ENOENT: no such file or directory, open '.../app/routes/helo.tsx'` from `compileRouteFile`: the route config is read at startup and every referenced module must exist. Fixing the path made `/hello` render `Hello ShopSphere` (HTTP 200); I then deleted the temporary route.

# Stage 1: JavaScript essentials

Setup: `node scripts/snapshot-products.mjs` pages through `GET /products` (the API caps `limit` at 60, so one `limit=100` curl returns 422) and merges all 308 products into `app/test/fixtures/products.json` (the full envelope; `data` is the array). Pure logic lives in `features/catalog/utils.ts` and `features/cart/totals.ts`; scratch checks run with `node scratch/<file>.ts` (Node 24 type stripping; added `allowImportingTsExtensions` to `tsconfig.json` so `.ts` specifiers typecheck).

Reality vs plan: prices in the API are integer **rupees** (not paise), products use `name` (not `title`) and `price` (not `basePrice`), `brand` is a plain string, and there are no variants on products yet. The cart layer works in integer paise (`toPaise(rupees)`), the catalog layer filters on the API's rupee `price`.

## 1.1 Destructuring, spread, rest, immutability

`updateQty`/`removeLine` (`features/cart/lines.ts`) and `toggle`/`deepFreeze` (`lib/immutable.ts`) return new arrays/objects. `scratch/01-immutability.ts` runs them on deep-frozen input and nothing throws; pushing to the same frozen array does throw a `TypeError`. Note `Object.freeze` on a `Set` does not stop `.add()`, so the toggle proof relies on the result being a different Set. `arr.push(x); setArr(arr)` does not re-render because React compares by reference (`Object.is`): same array, so state is "unchanged".

## 1.2 filter, map, find, some, every

`filterProducts` (`features/catalog/utils.ts`) is a conjunction of predicates; empty/undefined filters do not restrict (an empty brand list means "no brand filter", otherwise selecting then un-selecting a brand would show nothing). Brands use a `Set` for O(1) lookup, search lowercases `name + brand`. `scratch/02-filters.ts` asserts 5 combinations plus each filter alone; the expected counts came from an independent throwaway Python script over the JSON (not from the code under test), and the same values were seen in the `/scratch/explorer` UI (e.g. search "shirt" = 10, rating >= 4.5 = 82, Apple + rating >= 4.5 = 2).
Stretch done: `filterWithFacets` returns `{ items, facets.brands }` where brand counts ignore the brand filter itself (disjunctive facets). Selecting Apple still shows "OnePlus (4)" so users can widen the OR. The backend B1 facet counts must do the same, otherwise ticking one brand makes all the others read 0.
Pitfall seen in the explorer's number inputs: `Number("")` is `0`, so an empty box must map to `undefined`, not 0 (same trap as `z.coerce.number()` later).

## 1.3 reduce and groupBy

`computeTotals` (`features/cart/totals.ts`) is a `reduce` over lines in integer paise; the API sends rupees, so `toPaise()` (`lib/money.ts`) converts once at the edge. Rules chosen where the plan was ambiguous: free shipping when the *discounted* subtotal is strictly above 499.00 (exactly 499.00 still pays 40.00, asserted); empty cart ships nothing; percent discounts and tax are each rounded once with `Math.round`, so the parts add up to the total; a coupon below `minOrder` is ignored; a coupon never makes the subtotal negative. `scratch/03-totals-histogram.ts` has 8 hand-calculated carts (coupon hitting `maxDiscount`, below `minOrder`, rounding case, exact threshold).
`priceHistogram` uses integer-width buckets (`from`/`to` inclusive), so clicking a bar sets exact min/max rupee values; buckets always sum to `products.length`, empty input returns `[]`, equal prices return one bucket (no divide by zero), and a price range narrower than `bucketCount` returns fewer buckets. `brandCounts` uses `Map.groupBy` (needed `lib: ES2024` in `tsconfig.json`; it was ES2022). Float artefact check: `0.1 + 0.2 !== 0.3` but `toPaise(0.1 + 0.2) === 30`; `199.99 * 100` is `19998.999999999996`, hence the `Math.round`.
`[].reduce(fn)` with no initial value throws a `TypeError` (asserted), so an empty cart would crash the total; with `0` as initial value it returns `0`.

## 1.4 sort and comparators

`sortProducts` always uses `toSorted` (never `sort`) so the incoming array is untouched; `relevance` returns a copy in server order. `compareBy(...selectors)` composes comparators (first decides, later break ties) and compares strings with `Intl.Collator("en", { sensitivity: "base" })`. Tie-breaks for price/discount/newest: rating desc, then name; rating sorts by `ratingAvg` then `ratingCount` then name. `scratch/04-sort.ts` checks the original array (deep-frozen) is unchanged by reference and content, ties are ordered (5 neighbouring equal prices exist in the data), and that `["Zebra","Éclair"].toSorted()` puts "Éclair" after "Zebra" (UTF-16 code order) while the collator puts it next to "Eclair". `Array.prototype.sort` is stable in modern engines (asserted with a small stability case); `sort()` on frozen data throws, which is exactly the bug it would be on React props.

## 1.5 Optional chaining, nullish coalescing

`displayDiscount` and `safeBrandName` (in `features/catalog/utils.ts`) are checked in `scratch/05-defensive.ts` with `console.assert` (silent when green). `a || b` replaces every falsy value (`0`, `""`, `NaN`), `a ?? b` only `null`/`undefined`. ShopSphere example: a free-sample product with `price: 0` shown as `price || 99` becomes ₹99, which is a wrong price on screen; `price ?? 99` keeps `0`. Likewise a `discountPercent` of `0` must render as "No discount" deliberately, not because `0` was falsy.

## 1.6 Promises and async/await against the real API

Code: `lib/api/getJson.ts` (`getJson<T>` + `HttpError` with `status`), `lib/async.ts` (`sleep`, `withTimeout`, `isAbortError`), `features/catalog/homeData.ts` (`loadHomeData`), plus an "Async lab" panel on `/scratch/explorer` (buttons call the functions from event handlers, no effects). Verified two ways: `node --import ./scratch/register-alias.mjs scratch/06-async.ts` (the hook file teaches Node the `@/` alias) and in the browser panel.
- `fetch("/nope")` resolves with `ok: false, status: 404` (asserted); only `getJson`'s `if (!response.ok) throw` turns it into an error with the envelope message, e.g. `HTTP 404: Route not found: GET /api/v1/this-route-does-not-exist`.
- `loadHomeData` uses `Promise.allSettled`: the deliberately broken third URL ends up in `errors` while `newest` and `topRated` still hold 8 products each.
- `withTimeout(run, ms)` aborts via `AbortController` and races the abort signal, so even an operation that ignores the signal rejects. A 1ms timeout gives `error.name === "AbortError"`, which `isAbortError` tells apart from a real `HttpError`.
- Timings: `await a(); await b();` runs back to back (3 x `/products?limit=60` took ~47ms in the browser, ~20ms in Node), `await Promise.all([...])` overlaps them (~23ms / ~12ms); with `sleep(100)` twice it is 200ms vs 100ms. Local API latency is tiny so the difference is small in absolute terms. Not done: DevTools "Slow 3G"/"Offline" throttling and reading the Network panel waterfall (no manual DevTools in this automated run), the in-code timings stand in for it.

## 1.7 Modules and boundaries

Layout now matches plan 3.2: `features/catalog/{utils,types,homeData,index}.ts`, `features/cart/{totals,lines,types,index}.ts`, `lib/format.ts`, `lib/money.ts`, `lib/immutable.ts`, `lib/async.ts`, `lib/api/getJson.ts`. `features/*/index.ts` re-export an explicit named list (no `export *`) as the public API; the explorer route imports only from `@/features/catalog`. No file in `features/` or `lib/` imports `react` (grep'd). `formatCurrency(1299900)` gives `₹12,999.00` (2 decimals always; asserted in `scratch/07-format.ts`, including lakh grouping `₹12,34,567.89`).
Circular import, on purpose: `scratch/circular-broken/` (catalog imports cart, cart imports catalog's constant). Run with Node ESM it throws `ReferenceError: Cannot access 'CATALOG_NAME' before initialization` because cart.ts is evaluated while catalog.ts is still waiting for it (temporal dead zone); bundlers that emit `var`/CommonJS produce `"cart for undefined"` instead, the "undefined at runtime" symptom. Fix in `scratch/circular-fixed/`: move the shared constant into a leaf module (`names.ts`) that both depend on, so the graph is one-way. Barrel files can hurt tree-shaking because importing one name from the barrel makes the bundler load every module the barrel re-exports and, unless modules are provably side-effect free, it must keep them; in dev Vite also serves all of them. They also make accidental cycles easy (a feature file importing its own `index.ts`).
`npm run check:scratch` runs all scratch assertion files (the async one needs the backend running).

# Stage 2: TypeScript essentials

Added `zod@4` (4.6.7) as a dependency. Scope: a typed domain layer (`app/types/domain.ts`), discriminated unions, `unknown` at the boundary, generics for the API helpers, typed React building blocks, and Zod schemas that infer the types that cross the network.

## 2.1 Everyday types: modelling the domain

`app/types/domain.ts` holds `User`, `Address`, `Category`, `Brand`, `Product` (+ `ProductDetail`), `Variant`, `CartItem`, `Cart`, `Order`, `OrderItem`, `Payment`, `Review`, `Coupon`, `Deal`, with `Money` (whole rupees, as the API sends), `Paise` (cart layer only), `ISODateString`, `Id` aliases. Shapes follow the real B0 responses where an endpoint exists (users, categories, products) and the plan's data model otherwise (each marked "planned (Bn)"). No `any`.
What TypeScript / the real data revealed versus the plan's table:
- The plan says `title`, `basePrice`, `brandId`, `sellerId`, `variants`; the API sends `name`, `price`, `brand` (a string), `seller` (an id string), and no variants (one `sku` per product). Real shape wins.
- List and detail differ: `GET /products` has `categoryPath: string[]` (ids), `GET /products/:slug` has expanded `categoryPath` objects plus `description`, `highlights`, `specs`. Hence `Product` (list item) and `ProductDetail = Omit<Product, "categoryPath"> & {...}`.
- `User` uses `id` and `Category` uses `id`/`children`, products use `_id`.
- `products.json satisfies Product[]` fails with `Type 'string' is not assignable to type 'ProductStatus'`: JSON modules widen literals. Understood, not hidden: `app/test/fixtures/products.ts` is a typed loader that narrows `status` with a small runtime check (Zod takes over in 2.6). Everything else in the 308-product fixture already matched.
- `type` vs `interface`: I use `type` everywhere (unions, mapped/utility types, intersections all work with it; interfaces mostly matter for declaration merging and `extends` chains). Either is fine as long as the codebase is consistent.
- Rename: the cart layer's coupon rule is now `CouponRule` (paise) to avoid clashing with the domain `Coupon` (rupees, as stored/served).

## 2.2 Unions, narrowing, discriminated unions, exhaustiveness

- `lib/asyncState.ts`: `AsyncState<T>` (idle | loading | success{data} | error{error}) and `renderState`, whose `default: return assertNever(state)` forces every member to be handled. `lib/assert.ts` has `assertNever(x: never): never`. A minimal `ApiError` class lives in `lib/api/errors.ts` (the plan introduces it in Stage 6, but `AsyncState` needs something to hold).
- `features/orders/status.ts`: `statusLabel`, `statusColor`, `canCancel`, `canReturn`, each a `switch` over `OrderStatus` ending in `assertNever`. `features/orders/payment.ts`: `PaymentMethod` discriminated by `type`, `describePayment` (inside `case "razorpay"` the `razorpayOrderId` field is accessible; outside it would not compile).
- Exhaustiveness experiment: I added `"refunded"` to `OrderStatus` in `types/domain.ts` and ran `npm run typecheck`. It listed exactly the four switches to update, nothing else:
  `status.ts(27) / (49) / (68) / (87): TS2345 Argument of type '"refunded"' is not assignable to parameter of type 'never'.`
  I then handled `refunded` in all four (label "Refunded", tone neutral, cannot cancel, cannot return) and kept it in the union, so the final code includes it.
- Impossible state: with `{ isLoading: boolean; isError: boolean; data?: T }`, `{ isLoading: true, isError: true, data: [1] }` is a valid value (`scratch/08-unions.ts` shows it), and every consumer has to guess which flag wins. With `AsyncState` the same literal fails to compile (`@ts-expect-error` in the scratch file proves it), because `data` only exists on `"success"` and `status` is exactly one value.
- `scratch/08-unions.ts` also asserts `canCancel("delivered") === false` with `console.assert`.

## 2.3 `unknown` vs `any`, and untyped data

`lib/api/envelope.ts` has `ApiErrorEnvelope` and the hand-written guard `isApiError(x: unknown): x is ApiErrorEnvelope` (every check is a `typeof`/`in` narrowing; no `as` cast at all, so the "except inside the guard" allowance was not needed). `scratch/09-guards.ts` runs 15 malformed values (null, `{}`, `{success:true}`, missing/wrong-typed `code`/`message`, `success: "false"`) through it: all `false`.
`getJson` (`lib/api/getJson.ts`) now returns `Promise<unknown>`, uses `isApiError` to throw an `ApiError` with typed `status`/`code`/`details` (e.g. `code: "NOT_FOUND"`), and falls back to `code: "HTTP_ERROR"` when the failing body is not an envelope (a proxy's HTML 502). `HttpError` from Stage 1 is gone. `response.json()` is `Promise<any>` in `lib.dom`, so the helper annotates it as `unknown` immediately: that one line is the difference between "checked" and "unchecked" for everything downstream.
What stopped compiling when `getJson` returned `unknown` (`tsc` output): `homeData.ts` lines 20-22 (`Expected 0 type arguments`, since the old `getJson<ListResponse>(url)` was a pure lie, an `as` in disguise) and 31-32 (`'newest.value' is of type 'unknown'`). I fixed it with a hand-written `isProductList` narrowing in `homeData.ts`, deliberately tedious and shallow (checks only what the rails use): this is the cost Zod removes in 2.6. `any` is contagious because anything touched by it becomes `any` too (`const p = await res.json(); p.items.map(...)` silently typechecks with a typo like `p.itemz`); `unknown` forces narrowing before use.

## 2.4 Generics, practically

- `lib/api/envelope.ts`: `PageMeta`, `ApiSuccess<T>`, `ApiFailure`, `ApiResponse<T> = ApiSuccess<T> | ApiFailure` (discriminated by `success`), `Paginated<T> = { items: T[]; meta: PageMeta }`, plus the guards `isApiError` / `isApiSuccess`.
- `lib/api/client.ts`: `request<T>(path, init?)` unwraps the envelope (returns `data` or throws `ApiError`) and always sends `credentials: "include"`; `requestPaginated<T>` does the same for lists and returns `{ items, meta }`. Deviation: the plan's `getProducts` is "a one-liner over `request<T>`", but the API puts the list in `data` and paging in `meta`, so a second helper is needed to keep `meta`; both getters are still one-liners: `features/catalog/api.ts` (`getProducts(query)`, `getProduct(slug)`) over them. The one `as T` / `as T[]` in the client is commented as the "trusted generic" that 2.6 removes the need for.
- Utility types: `ProductCardData = Pick<Product, "slug" | "name" | "images" | "price" | "mrp" | "ratingAvg">` (real field names, not the plan's `title`/`basePrice`), `CartItemInput = Omit<CartItem, "priceSnapshot">`, `ProductQuery = Partial<{ page, limit, sort, ... }>` (all params optional). `Awaited<ReturnType<typeof getProducts>>` yields the page type (see `scratch/type-tests.ts`).
- `lib/groupBy.ts`: `groupBy<T, K extends PropertyKey>(items, key): Record<K, T[]>`, now used by `brandCounts` (the brand facet); a boolean-returning selector is rejected because `K` must be a `PropertyKey`.
- `scratch/type-tests.ts` is compile-time only: `// @ts-expect-error` lines prove that `Promise<Product[]>` is not `Promise<string>` and that `getProducts()` is not `Promise<Paginated<Order>>`; if one ever starts compiling, `tsc` reports an unused directive. `scratch/10-generics.ts` runs the real calls against the API (filters, detail by slug, 404 -> `ApiError`, `limit=1000` -> 422 `VALIDATION_ERROR`).
- Reading `Record<string, Pick<Product, "title">[]>` aloud: "a record from strings to arrays of products, where each product only has its title" (an object whose every key is a string and whose every value is a list of title-only products).
- Scratch plumbing: `lib/env.ts` now also exposes `env.DEV`; Node has no `import.meta.env`, so the scratch resolver hook maps `@/lib/env` to `scratch/env-node.ts`. `npm run check:scratch` runs every numbered scratch script.

## 2.5 Typing React code

- `components/common/Rating.tsx`: `{ value; count?; size?: "sm" | "md" } & React.ComponentProps<"div">`, native div attributes (`title`, `data-*`, `className`) pass through; `role="img"` + `aria-label` for accessibility.
- `components/common/List.tsx`: generic `List<T>({ items, getKey, renderItem, empty })`. `T` is inferred from `items`, no annotation, and is used for the 308 products and for the sample orders (`test/fixtures/orders.ts`) on `/scratch/explorer`.
- `hooks/useToggle.ts`: returns `[value, toggle, setValue] as const`, so destructuring gives a typed tuple (`boolean`, `() => void`, `(v: boolean) => void`) rather than an array of the union of those three.
- `components/common/QuantityInput.tsx`: controlled `<input type="number">` with `React.ChangeEvent<HTMLInputElement>`; it parses with `valueAsNumber` (NaN for empty/garbage, which is ignored), truncates and clamps to `min`/`max` (typed 50 with `max=10` shows 10 in the browser). Props are `Omit<React.ComponentProps<"input">, "value" | "onChange" | "type" | "min" | "max">` plus our own `value`/`onValueChange`, so the native props stay available but the ones we own cannot conflict.
- `scratch/type-tests-react.tsx` (compile-time only): `List` infers `Product`; `renderItem={(p) => p.title}` fails (the plan's old field name; the real one is `name`); a `renderItem` typed for `Order` with product items fails; `useToggle()` has no 4th element; `size="xl"` and `value="1"` are rejected.
- No `React.FC`. Trade-off in one sentence: `FC` used to add an implicit `children` and made generic components awkward (a const arrow cannot carry `<T>` cleanly), while a plain function with a typed props object gives accurate `children`, works with generics and keeps the return type honest.
- Verified in the browser at `/scratch/explorer`: toggle button, qty clamping, rating (309 `role="img"` nodes = 308 products + 1), orders list; no console warnings. `Route.ComponentProps` is not needed yet (no route params until Stage 5).

## 2.6 Zod 4: runtime schemas and `z.infer`

- `lib/api/schemas.ts`: `pageMetaSchema`, `apiEnvelopeSchema(dataSchema)`, `paginatedSchema(itemSchema)` (full list envelope with required `meta`). Deviation: the plan puts these in `features/catalog/schemas.ts`; they are generic, and `lib/` must not import from a feature, so they live in `lib/api/`. `features/catalog/schemas.ts` has `productSchema`, `productDetailSchema` (`.omit({categoryPath}).extend({...})`), `productQuerySchema`, and the types: `Product`, `ProductDetail`, `ProductStatus`, `ProductSort` are all `z.infer<...>`. The hand-written `Product`/`ProductDetail`/`ProductStatus` were deleted from `types/domain.ts` (no duplicate remains), and the Stage 2.1 fixture loader is replaced by `paginatedSchema(productSchema).parse(raw)`, so all 308 snapshot products are validated by the same schema the live API goes through (the snapshot script now also writes `hasNext`/`hasPrev` into `meta`).
- `request<T>(path, { schema })` / `requestPaginated`: when a schema is passed, `T` is inferred from it (`request("/x", { schema: productSchema })` is `Promise<Product>`; `scratch/type-tests.ts` proves a wrong annotation fails) and a mismatch throws `ContractError` (message with request, path and first issue; all issues are logged to the console with `console.error`).
- Break the contract on purpose (`scratch/11-zod.ts`): a schema expecting `title` instead of `name` gives `API contract mismatch for /products?limit=2 at data.0.title: Invalid input: expected string, received undefined`; a schema with `price: z.string()` gives `... at data.0.price: Invalid input: expected string, received number`. The path pinpoints the exact element and field instead of a `NaN` three screens later.
- Stretch (recommended) done: validation runs only when `env.DEV` (`VALIDATE` in `client.ts`). Trade-off: faster production with no schema cost on big lists and no user-facing crash on a harmless extra/odd field, but the types become claims again in production (one `as T` in the client is that trusted path) and a real contract break shows up later as `undefined`/`NaN`, so production needs error reporting (Stage 14) to compensate. Alternative if validation is cheap enough: validate everywhere and report to Sentry.
- `parse` vs `safeParse`: `parse` throws a `ZodError` (fine in a fixture loader or where a failure should abort); `safeParse` returns `{ success: true, data } | { success: false, error }` (use it where you want to branch or build your own error, as the client does). `z.infer` (= `z.output`) is the type after transforms/defaults/coercion, `z.input` is what you must feed in: for `productQuerySchema`, `brand` is `"Apple,boAt"` as input and `string[]` as output, and `page` is `unknown` as input (coerce accepts anything) but `number` as output (`scratch/type-tests.ts`).
- `z.coerce.number()` for query strings, and its pitfall: it runs `Number(input)`, and `Number("")` is `0`, so an empty `?minPrice=` becomes "minimum price 0" and passes silently (`naiveMinPriceSchema.parse("") === 0`, asserted). `productQuerySchema` guards it with `z.preprocess` (`queryNumber`: "" becomes undefined before coercion); `.optional()`/`.default()` must be inside the preprocess, otherwise the undefined turns into `NaN` and fails (hit this while writing it).
- Zod 4 notes: `z.url()`, `z.iso.datetime()` are top-level now (not `z.string().url()`); error objects expose `.issues`; unknown keys are stripped by default (`__v` disappears from `Product`).
- Verified: `npm run typecheck`, `npm run build`, `npm run check:scratch` (all 12 scratch scripts), and the `/scratch/explorer` page in the browser (fixture parsed by Zod, validated live API calls from the async lab, no console errors apart from the expected 404 of the deliberately wrong route).

## 4.2 Fetching data in an effect: loading, error, success

- `features/catalog/hooks/useProducts.ts` (hand-rolled, to be deleted in Stage 9): `useProducts(params): AsyncState<Paginated<Product>> & { reload }`. The return is still the discriminated union (the `reload` function is intersected into every member, needed for Retry). Used by the live `/products` route (`routes/products.tsx`, page in `useState`, 12 per page) with `ProductCardSkeleton`, `ErrorState` (message shown, code logged in the hook) and `EmptyState`; `features/catalog/api.ts` gained `getProductsByQuery(queryString, signal?)`. `lib/api/errors.ts` gained `toApiError(unknown)`: `fetch` rejects with a `TypeError` ("Failed to fetch") that has no status, and Zod mismatches are `ContractError`; both become an `ApiError` (`NETWORK_ERROR`, `CONTRACT_ERROR`) so the UI has one error type.
- Two design decisions that came from the linter and from the plan's "common mistakes": (1) the dependency is the query STRING (`toQueryString(params)`), a primitive; the `params` object is new on every render and would re-run the effect forever. (2) `loading` is derived, not stored: the state holds `{ key, status, ... }` for the request it answers and `key !== current key` means loading. The obvious version calls `setState({ status: "loading" })` synchronously in the effect, which `react-hooks/set-state-in-effect` rejects (extra render, one stale frame showing the previous page's data as "success" for the new page).
- Retry: a `reloadKey` in state is part of the request key and of the effect's dependencies, so `reload()` re-runs the effect.
- Verified in the browser: page 1 shows 12 cards, "Page 1 of 26" (308 products / 12); Next fetches `page=2&limit=12`; with the backend stopped, Next gives the alert "Failed to fetch" with a Retry button; after restarting the backend, Retry recovers. The loading skeleton is too brief to catch on localhost (response in a few ms), the layout is a same-shaped grid of 12 placeholders (`aria-busy`); I did not throttle the network to screenshot it.
- Network tab: dev (StrictMode) `page=1` is requested twice on load and once per later page change; the production build (`npm run build`, `vite preview` on :3000 because the backend CORS only allows :5173 and :3000) shows exactly one request on load and one per page change. Why: StrictMode mounts, unmounts and re-mounts every component once in dev, so the mount effect runs twice; in production it runs once.
- Idea to avoid the flash when changing page (written down as the plan asks): keep showing the previous page's data (dimmed) while the next one loads, i.e. `keepPreviousData`/`placeholderData` in Query (Stage 9). Today the grid is replaced by skeletons on every page change.
- Skipped stretch (`lastUpdated`/`useNow`).

## 4.3 Cleanup, AbortController and race conditions (part 1: the race)

- `request<T>` already accepted a `signal`: its options extend `RequestInit` and `send` spreads them into `fetch`, so step 1 needed no change; I only threaded an optional `signal` through `getProducts` / `getProductsByQuery` / `getHealth`.
- Race reproduced on `/scratch/effects` (`app/scratch/effects/SearchRaceDemo.tsx`; fake latency makes "watch" take 1.5 s and anything else 150 ms, instead of DevTools throttling, so it is deterministic): type "watch" then immediately "cream". `NaiveSearch` (effect without cleanup) ends as `Input: cream / showing: watch (8)`: the older request answered last and overwrote the newer result. `AbortSearch` (cleanup calls `controller.abort()`, `AbortError` ignored) ends as `Input: cream / showing: cream (3)`. The same cleanup is now in `useProducts` (fast clicks on Next/Previous cannot show page 2 after page 3).
- Why `AbortError` is not an error to show: it is raised by OUR cleanup, on purpose, for a request nobody is waiting for any more; the user did nothing wrong and the newer request is already in flight. Treating it as a failure would flash an error between keystrokes. The catch therefore checks `isAbortError` and returns without touching state.
- Timeline (for checkpoint Q3): without abort: `t0 send(watch)`, `t1 send(cream)`, `t2 cream answers -> UI shows cream`, `t3 watch answers -> UI shows watch (WRONG)`. With abort: `t1` cleanup aborts watch (browser status `(canceled)`, the promise rejects with AbortError, ignored), `t2 cream answers -> UI shows cream`, and nothing arrives at t3.
- Backend finding that shapes the SearchBox: `search` is a MongoDB full-text (whole word) search: `search=watch` gives 8 products, `search=wat` gives 0, `search=smartwatch` gives 22. Prefix typing therefore shows "No results" until a word is complete. Noted for B1 (autocomplete/suggest endpoint); the box shows the honest result of the real API.

## 4.4 Custom hooks and the Rules of Hooks: useDebounce

- `hooks/useDebounce.ts`: `useDebounce<T>(value: T, delayMs): T` (state + effect with `setTimeout`, cleanup clears the timer on every change and on unmount) and `useDebouncedCallback(fn, delayMs)` (stable function via `useCallback`, latest `fn` kept in a ref so it never calls a stale closure, timer cleared on unmount). The search box needs the VALUE version: it must feed a request effect that has its own cleanup (cancellation), and a debounced function would also have to be recreated or protected from stale closures; the callback version is for fire-and-forget events (analytics, autosave). Verified (`/scratch/effects`): typing "abc" in input A at 100 ms intervals leaves A's debounced value empty during typing and `abc` after 500 ms of silence; input B (another `useDebounce` call) stays empty, because each call of a hook owns its own `useState` slot and timer: a custom hook shares logic, not state.
- Rules of Hooks broken on purpose (`app/scratch/rules/ConditionalHook.tsx`, route `/scratch/rules`, with a file-level eslint-disable that names the reason): the hook sits in `if (enabled)`. ESLint reports `react-hooks/rules-of-hooks` statically. At runtime the first render calls 2 hooks, after the click 3, and React throws `Rendered more hooks than during the previous render`, with a dev table that lines up "Previous render / Next render" and shows `3. undefined useState`. They exist because React stores hook state as an ordered list per component and identifies each hook only by its position in that list; a conditional or looped call shifts everything after it onto the wrong slot.

## 4.5 useRef: DOM access and mutable boxes

- `hooks/useFocusShortcut(ref, key = "/")`: a `keydown` listener on `document`, installed in an effect and removed in its cleanup; it ignores events from inputs/textareas/selects/contenteditable (so typing "/" in a field stays a "/") and modifier combinations, calls `preventDefault()` (else the "/" would be typed into the box it just focused) and then `ref.current?.focus()`. Listener lifecycle (`/scratch/refs`, mount/unmount toggle, `addEventListener`/`removeEventListener` patched to count `keydown`): 3 mount+unmount cycles gave 6 adds and 6 removes (3 real + 3 extra from StrictMode's mount-unmount-mount), i.e. always balanced.
- `hooks/usePrevious(value)` **deviates from the classic recipe**: the ref version (`useEffect(() => { ref.current = value })` then `return ref.current`) reads a ref during render, which the plan's own acceptance criterion ("no ref is read during render for UI output") and the react-hooks `refs` rule reject. ## 4.6 Timers and useCountdown: the flash-sale strip

- `hooks/useCountdown(endsAt, { serverOffsetMs, tickMs })` returns `{ remainingMs, days, hours, minutes, seconds, isExpired }`. It stores NOTHING per tick: remaining time is `max(0, endMs - (now + serverOffsetMs))` where `now` comes from `hooks/useNow`. Subtracting 1 s per tick (`setSeconds(s => s - 1)`) drifts (each interval fires late) and freezes while a background tab is throttled; `end - Date.now()` is correct whenever it is evaluated, so after a 3-minute background pause the first tick shows the right time. `lib/duration.ts` has the pure `splitDuration`/`formatCountdown` (seconds round up, so 00:00:00 means "over"); `scratch/13-duration.ts` asserts it.
- Server offset: `serverOffsetMs = serverTime - clientTime`. The deal ends at a server instant, so the client corrects its clock by the offset (a user whose clock is 5 minutes fast would otherwise see the sale end 5 minutes early). `features/deals/hooks/useServerTimeOffset.ts` is the stub the plan asks for: it returns 0. **B4 is not built, so there is no deals/time endpoint; the fallback is the stub plus a fake `endsAt = now + 90 min` fixed at mount.** (The existing `GET /health` already returns `time`, a candidate for Stage 11.)
- Stretch (recommended) done: `hooks/useNow(tickMs, stopAt?)` is a module-level store with ONE `setInterval` per tick length, consumed through `useSyncExternalStore` (tear-free, no "setState in an effect"). The interval exists only while someone is subscribed; a subscriber that passes `stopAt` is dropped automatically when `now >= stopAt`; a `visibilitychange` listener refreshes the clock immediately when a tab becomes visible. Cost of five independent `setInterval`s would be five timers, five wake-ups per second and, with `useState`, five separate render passes; sharing gives one wake-up and one batch.
- Verified on `/scratch/countdown` (browser): five countdowns (ending in 3 s, 60 s, 1 h, 1.5 h, 2 days) shown `00:00:00 ended`, `00:00:53`, `00:59:53`, `01:29:53`, `1d 23:59:53`; "Count intervals" says 1 interval running (`activeNowTimers()`), 0 after unmounting them, 1 again after remounting; the expired one's commit counter stayed at 7 over 3 s while a live one went to 19, i.e. no further renders after zero (I counted commits with a ref instead of the React Profiler); the flash-sale strip with a 6 s deal flips to "Deal ended", badges say "Deal ended" and the add-to-cart buttons disable. The home page strip (live API, 4 deepest discounts, fake claimed bars, one shared countdown) shows `01:29:55` then `01:29:53` two seconds apart.
- NOT verified: the 3-minute background-tab pause (cannot be done with this browser tool; the design argument above is the evidence) and the Profiler/Performance-monitor views.
- A lint lesson: `react-hooks/purity` rejected `Date.now()` in render in my first `useCountdown` (used for the "invalid date" fallback). `Date.now()` in render is non-idempotent; the clock enters only through the store (`useNow`), and an invalid date now means `stopAt = 0`.

## 4.7 Browser-API hooks: useLocalStorage, useMediaQuery, useOnClickOutside

- `hooks/useLocalStorage<T>(key, initial, validate?) -> [value, setValue, remove]`, built on `useSyncExternalStore`. Decisions: (1) the snapshot is the raw STRING, because strings compare by value; returning a parsed object from `getSnapshot` would be a new reference on every read and loop forever; the parsed value is `useMemo`'d from the raw string. (2) `initial` is frozen in `useState` so an inline `[]` default does not change identity per render. (3) Corrupt JSON, or JSON of the wrong shape (an optional type-guard `validate`), falls back to `initial` instead of throwing. (4) `getItem`/`setItem` are wrapped in `try/catch` (quota, private mode, blocked storage) with an in-memory `Map` fallback. (5) The browser fires `storage` only in OTHER tabs, so writes also dispatch a same-tab `CustomEvent`; both feed the same subscribe function. (6) `setValue` accepts a functional update and reads the freshest stored value, not a render-time snapshot.
- `hooks/useMediaQuery(query)` (also `useSyncExternalStore`, `matchMedia(...).addEventListener("change")`) drives `components/layout/Header.tsx`: `(min-width: 1024px)` renders `MegaMenu` (disclosure panel, outside click and Escape close it) and otherwise `MobileMenu` (left `Sheet` drawer); only one is in the DOM. Verified by reloading at 800 px (only the "Open menu" button exists, no "Categories") and at 1200 px (only "Categories"; opening the panel and a pointerdown outside closes it). **Not verified: live switching while resizing**: the emulated viewport of the browser tool never fires `matchMedia` `change` events (a plain raw listener I added in the page received 0 events too), so only the initial evaluation could be tested; the subscribe path is the standard one.

## 4.8 useMemo, useCallback, memo: measure first

Lab at `/scratch/memo` (`app/scratch/memo/MemoLab.tsx`): 1,000 products (the 308 fixture products, unique ids), the list filtered over all 1,000 but only the first 200 rows rendered (real `ProductCard`s), three row modes, and two instruments: a counter bumped in an effect-without-deps in each row (counts committed row renders) and a React `<Profiler>` whose `onRender` collects commits and `actualDuration` (scriptable, so I did not use DevTools screenshots; numbers are dev-mode with StrictMode, so absolute ms are inflated). Results (my run):

| mode | click "unrelated state +1" | type "sony" (4 keystrokes) |
| --- | --- | --- |
| plain rows | 200 row renders, 1 commit, 115 ms | 368 renders, 112 ms |
| `memo(Row)` + inline `onAddToCart={() => ...}` | 200 renders, 46 ms (no improvement in renders) | 368 renders, 164 ms |
| `memo(Row)` + `useCallback` handler | **0 renders**, 0.8 ms | 198 renders (only the NEW rows mount), 99 ms |

- Why `memo` with an inline `onClick`/callback is useless: `memo` skips a render only if every prop is `Object.is`-equal; an arrow function written in the parent's render is a new object every render, so the comparison fails every time and you pay for the comparison on top of the render. It starts helping only when the callback identity is stable (`useCallback`) and the other props are stable too (the `product` objects are the same references, because `filtered` is memoized).
- `useMemo` on real work: `console.time` for 100 runs over 1,000 products: `priceHistogram` 7.9 ms (0.08 ms each), `filterProducts` 36 ms (0.36 ms each). Both are far cheaper than rendering the rows (tens of ms), so memoizing them is not needed for speed; I kept `useMemo` on `filtered` and `histogram` in the lab only because `filtered` must keep its identity for `memo` rows (referential stability, the second legitimate reason). `useMemo` that costs more than it saves: a micro-benchmark (the "Benchmark" button; it re-creates what the hook does, allocating the callback and comparing a deps array, vs. just computing) for the trivial `i * 2`: 8.0 ms direct vs 38.8 ms memo-like for 2,000,000 iterations (~5x slower), i.e. the cache bookkeeping is the expensive part.
- One case where memoization changes nothing: typing in the filter changes `filtered`, so the visible rows are different products anyway (new keys mount, nothing to skip; 368 vs 198 renders is only the already-mounted rows being spared); also any component whose props change on every render. One case where it is essential: a big list under a parent with unrelated frequently-changing state (countdowns ticking above a product grid, the cart drawer open state): the "+1" button went from 200 renders to 0.
- Mistakes avoided: no blanket `useMemo`/`useCallback` in the real code (none in `ProductCard`, `Gallery`, `SearchBox`); the React Compiler (Stage 13 preview, not enabled) would insert this memoization automatically, which is why knowing the manual version matters mostly for reading and diagnosing code. Profiler's "why did this render" panel was not used (no GUI); the counters above answer the same question for these cases.

## 4.9 Stale closures and functional updates

Demos on `/scratch/closures` (`app/scratch/closures/StaleClosures.tsx`; broken variants are kept and named `Broken...`, each with its fix next to it):

1. **Batched updates in one handler.** `BrokenTripleIncrement`: `setQty(qty + 1)` three times. One click ends at 1, not 3 (observed `1`), because `qty` inside the handler is the value of the render the handler belongs to ("state is a snapshot"); all three calls say "set to 0 + 1". `FixedTripleIncrement`: `setQty(q => q + 1)` x3 ends at 3 (observed `3`); the updater functions are queued and each receives the result of the previous one.
2. **Interval reading state.** `BrokenIntervalClosure`: `useEffect(() => { setInterval(() => setLogged(qty), 400) }, [])`: the effect and its callback were created in the first render, so they close over `qty = 0` forever. After clicking + three times (qty = 3) the interval still logged `0`. (The linter's `exhaustive-deps` rightly complains; the broken file carries an eslint-disable naming the reason, because "silence the rule to stop re-running the effect" is exactly how this bug is born.) Three fixes, all verified (`qty = 3`, logged `3`): **A** add `qty` to the dependency array (correct and simplest; the interval is torn down and recreated on every change, which is cheap here but resets timing), **B** `useLatest(qty)` ref (new `hooks/useLatest.ts`, the stretch) read as `latestQty.current` inside the callback; the interval is created once, **C** `useEffectEvent` (React 19.2): `const onTick = useEffectEvent(() => setLogged(qty))`, the effect calls `onTick()` and does not list it: an Effect Event is non-reactive logic that always sees the latest props/state; it must not be in the dependency array or passed around (it is only valid called from effects).
- When to use which: **dependency array** when the effect should genuinely re-synchronise whenever the value changes (a fetch keyed by a query, a subscription keyed by an id); **functional update** when the next state is computed from the previous state of the SAME state variable (counters, toggles, appending to a list), no dependency needed; **ref / `useEffectEvent`** when a long-lived callback (interval, listener, socket handler) must read the latest value but must NOT restart when the value changes.

## 4.10 Bug-hunt: five broken effects (`/scratch/bugs`, `app/scratch/bugs/`)

Each bug keeps its broken version and its fix side by side (`BugNBroken` / `BugNFixed`), mounted on `/scratch/bugs`. Observations from the browser:

### Bug 1: infinite fetch loop
Symptom: identical `GET /products?limit=3&sort=newest` requests keep firing and the page never settles (the demo has a safety cap of 15; the real bug has none): "Count requests" showed 15 for the broken one. Cause: `const params = { limit: 3, sort: "newest" }` is created in render and used as the dependency; each response calls `setNames`, which re-renders, creates a new object (new identity) and re-runs the effect. Fix: depend on the primitives (`[limit, sort]`): the fixed one made 2 requests (StrictMode's double mount in dev) and stopped. The linter warns about exactly this (`exhaustive-deps`: "makes the dependencies change on every render"); the broken file suppresses it with a reason.

### Bug 2: missing cleanup on `resize`
Symptom: every time the component is shown again the number of window `resize` listeners grows and old handlers keep calling `setState` on components that are gone. Cause: `addEventListener` in the effect with no `removeEventListener`. Fix: return a cleanup. Measured with counters (3 hide/show cycles on each version): added 16, removed 7, so 9 listeners alive; the fixed component accounts for exactly 1 (the mounted one), the other 8 are the broken version's leaks (4 mounts x 2 for StrictMode).

### Bug 3: race on a slow category switch
Symptom: click "mobiles" (made slow: 1.5 s) and then "laptops" (0.1 s): the UI says `selected laptops / showing mobiles: Google F14 Smartphone 5G`. Cause: no cleanup; the older response arrives last and overwrites the newer. Fix: `AbortController` in the effect cleanup, `AbortError` ignored: `selected laptops / showing laptops: Apple K21 Laptop`. (The artificial `sleep` is not abortable; the aborted request still starts after the delay but dies immediately with an already-aborted signal.)

### Bug 4: stale closure in an interval
Symptom: a timer incrementing every 200 ms shows `1` and stays there (broken) while the fixed one kept counting (56 after ~11 s of the page being open). Cause: the effect runs once (`[]`), and `setSeconds(seconds + 1)` closes over the first render's `seconds = 0`, so it always sets 1. Fix: `setSeconds(s => s + 1)`: the new value depends only on the previous one, so the effect needs no dependency and the interval is created once.

### Bug 5: `useEffect` that derives state, one frame of wrong UI
Symptom: after each click on "+" the displayed total disagrees with `qty * price` for one committed frame (and there are two commits per click). Cause: `total` is stored state updated by an effect that runs after the commit in which `qty` changed. Measured with a no-deps effect that compares the committed total with `qty * price`: broken 13 commits / 3 wrong frames, fixed 10 commits / 0 wrong frames (the same numbers pattern as 4.1). Fix: `const total = qty * PRICE` in render; `react-hooks/set-state-in-effect` flags the broken version.

The five fixes in one line each: (1) primitive deps instead of an object, (2) return a cleanup that mirrors the setup, (3) abort the previous request in cleanup, (4) functional update instead of closing over state, (5) derive during render, no state, no effect. Skipped stretch: the "Effect decision tree" page (the checkpoint answers contain the same decision logic).

## 5.1 Router modes and the route config

- **Declarative mode**: `<BrowserRouter><Routes><Route path element/></Routes></BrowserRouter>`. Routes are JSX, you render the router yourself, no data APIs. **Data mode**: `createBrowserRouter([{ path, element, loader, action, errorElement, children }])` + `<RouterProvider>`; loaders/actions, `useNavigation`, `useFetcher`, route-level error elements. **Framework mode** (what this app is): the Vite plugin (`@react-router/dev`) reads `app/routes.ts` (file references, not elements), generates `+types` per route, splits every route module into its own chunk, handles `meta`/`links`/`handle`/`ErrorBoundary` exports, and can SSR. Hooks and components (`Link`, `Outlet`, `useParams`, `useSearchParams`...) are identical in all three, so skills transfer. What differs: how the tree is declared (JSX vs object vs `routes.ts`), data APIs (none vs loaders/actions), and build integration (none vs plugin-owned `root.tsx`, typegen, code splitting). With `ssr: true` the same tree would also render on a server per request, so routes could not touch `window`/`localStorage` during render and `clientLoader` vs `loader` starts to matter. We stay at `ssr: false`: the build is static files plus an `index.html` shell.
- `layout(file, children)` adds a wrapper and NO url segment (the shell, the guards later); `route(path, file, children)` adds a url segment and also wraps its children (`/account` + `profile` = `/account/profile`); `index(file)` renders at the parent's exact url. `/checkout` renders nothing itself: its index route redirects to `/checkout/address`.
- All 28 rows of the route map (plan 2.2) render a placeholder heading (checked by navigating to each URL in the browser and reading the `<h1>`); unknown URLs hit `route("*")`. `npm run typecheck` regenerates the `+types` files without errors.
- Reorganisation: the earlier-stage labs moved from `/scratch/*` to `/dev/*` (behind a `dev` layout that renders nothing in production builds); the 3.1 grid lab (`/scratch/grid`) became `/dev/keys` because the real listing replaces it.
- Stretch (reading old tutorials): the same tree as `createBrowserRouter([{ path: "/", Component: Shell, children: [{ index: true, Component: Home }, { path: "products", Component: Products }, { path: "c/:categorySlug", Component: Category }, ...] }])`: `layout()` is a children array under a route with no `path`, `route(path, file, kids)` is `{ path, children }`.

The patterns must mirror `routes.ts`; there is no compile-time link between them (RR's `href()` helper could be a later improvement).

The page uses `useProduct(slug)` (`GET /products/:slug` through the new `hooks/useAsyncResource`, the 4.2/4.3 pattern made reusable: abort in cleanup, derived loading, reload) and four states: loading, 404, other error (retry), content. Reset on navigation: the loading branch of the page unmounts `ProductDetailView` for each new slug while the fetch is in flight, so with fetch-on-every-navigation the state resets anyway; `key={product.slug}` is what keeps it correct once data is instantly available (Stage 9 cache), and `?bug-no-key` still removes it for the 3.5 demo. ## 5.4 URL as state: filters, sort and pagination

- `features/catalog/filters.ts`: `parseFilters(searchParams, defaults?)` (Zod object with `.catch()` per field) and `toSearchParams(filters, defaults?)` (omits defaults), plus `toProductQuery` (URL filters -> API query) and `countActiveFilters`. Named the type `ListingFilters` because `ProductFilters` already means the Stage 1 predicate type. `scratch/14-filters.ts` (part of `npm run check:scratch`) asserts garbage handling: `page=-5|abc|2.5|99999999` -> 1, unknown sort -> relevance, `minPrice=abc` and `maxPrice=` (empty) -> absent (not 0), rating 9 -> absent, blank/duplicate brands dropped, a reversed price range is swapped (the API would answer 422), and a round trip keeps a full URL identical while defaults vanish.
- `hooks/useProductFilters()` returns `{ filters, setFilter, toggleBrand, setPriceRange, clearAll, activeCount }`. There is NO `useState` copy of the filters: `filters` is `useMemo(parseFilters(searchParams))`, writes go through `setSearchParams(prev => ..., opts)` reading `prev` (not a stale render). Every change resets `page` to 1 unless the patch sets its own page. Verified in the browser: ticking Apple + Bajaj on page 2 then choosing "4 stars & up" gave `?brand=Apple&brand=Bajaj&minRating=4` (no `page`), and a page change keeps the filters.
- History: checkboxes, radios, sort, bars and page changes PUSH; typing in the price boxes is a draft in the input for 500 ms (`useDebouncedCallback`) and then ONE `replace`. Measured with RR's `history.state.idx` (the browser caps `history.length` at 50, so length is useless): typing `2, 20, 200, 2000, 20000` quickly left `idx` unchanged (3 -> 3) and produced exactly one request, `minPrice=20000`; a histogram bar click went to idx 4, a page change to 5, and Back returned to the bar state. Back/Forward through brand ticks moved one filter at a time.
- Scroll: RR scrolls to the top for every new location, which is wrong when the user is working in the sidebar, so filter changes pass `preventScrollReset: true` and only page changes reset the scroll.
- UI (`features/catalog/components/`): `ProductListingPage` (shared by `/products` and `/c/:categorySlug`; the category is the preset from the path, so category links are real URLs and keep the other filters but drop `page`), `FilterSidebar` (`CategoryList` from `GET /categories` with counts, brands with facet counts, `PriceRangeFilter` with Stage 1's `priceHistogram` bars + two number inputs, rating radios, in-stock checkbox), `SortSelect`, `ActiveFilterChips` (each removable, "Clear all"), `Pagination` (1 ... 4 [5] 6 ... 20 window, `aria-current`), grid/list toggle. Facets stay visible while the next page loads (last known facets are kept with a guarded set-state-in-render). Out-of-range page (`?page=500`) shows "Page 500 does not exist" with a button to page 1, not a blank screen.
- Disjunctive counts: brand counts are computed with every filter EXCEPT the brand filter, so after ticking Apple the Samsung checkbox still shows how many Samsung products match the other filters (otherwise it would read 0 and you could never widen the OR); a normal "conjunctive" count would also apply the brand filter and zero everything else. The price facet ignores the price filter (so the boxes keep their placeholders), the rating facet ignores the rating filter, in-stock ignores itself.
- Histogram caveat: the API has no price buckets, so the bars come from a 60-product sample of the category (`usePriceHistogram`, one extra request per category, not per filter). An exact server-side bucket facet would be the proper fix.
- Mobile (360 px emulation, then reload because `matchMedia` change events do not fire in the tool's emulation): `/c/mobiles` shows no inline sidebar, a "Filters" button opens a `Sheet`, ticking Apple updates the URL and the count ("Show 3 results"), the close button closes it and focus is back on the "Filters (1)" trigger (base-ui dialog returns focus).
- Stretch (recommended) done: the last explicit `sort`/`view` are stored under `shopsphere.listingPrefs` and become the defaults when the URL does not say (explicit URL always wins; the URL omits values equal to the default). Trade-off: a shared URL without `sort` shows the recipient's preference.
- Header/mobile menus now render the real category tree (`useCategoryTree`, one shared cached request, replaces the static `categories.ts`).

## 5.5 Navigation, redirects, scroll and focus

- Login stub (`routes/login.tsx`): `navigate(getReturnTo(location.state), { replace: true })`. `features/auth/returnTo.ts` accepts only same-origin paths starting with a single `/` (so `state.from = "//evil.com"` or `"https://..."` falls back to `/`, an open-redirect guard) and never returns to `/login`. `from` is `pathname + search + hash`, so deep links with query strings survive (wired by the guard in 5.6).
- Fake order: `routes/checkout/review.tsx` calls `navigate(paths.orderSuccess(id), { replace: true })`. Plan acceptance says Back must not return to checkout. A single `replace` is NOT enough if every checkout step was pushed: Back would land on the payment step. So the step links (Back / Continue) and the `/checkout` -> `/checkout/address` redirect also use `replace`, which means the whole checkout occupies ONE history entry. Verified with RR's `history.state.idx`: `/cart` idx 1, `/checkout/address` idx 2, review idx 2, success idx 2, and Back went to `/cart`. Trade-off: the browser Back button inside checkout leaves checkout instead of stepping back one step (the in-page Back link does that).
- Redirects: `/checkout` -> `/checkout/address` and legacy `/products?category=x&brand=...` -> `/c/x?brand=...` (`page` dropped) are `<Navigate replace>`; with `replace` the redirecting URL never enters history, otherwise Back would bounce straight back to the redirect.
- `hooks/useRouteFocus(mainRef, liveRef)` (used in `shell.tsx`): after a PATHNAME change it focuses the page `<h1>` (`tabindex=-1`, `preventScroll`) and, 150 ms later, writes `document.title` (or the h1 text) into a polite `role="status"` live region. Not on first load (a ref compares the last pathname, which also makes StrictMode's replayed effect harmless) and not on search-param changes (ticking a filter must not move focus). Lint (`react-hooks/immutability`) rejected `element.tabIndex = -1` on a ref-derived node; `setAttribute("tabindex", "-1")` is accepted. Verified in the browser: after navigating to `/checkout`, `document.activeElement` is `H1 "Delivery address"` and the live region reads the same. NOT verified: an actual VoiceOver pass (no screen reader in this environment).
- Scroll restoration (`<ScrollRestoration/>` in `root.tsx`, framework SPA): on `/products` scrolled to 588 px, opened a product (scrollY 0 on the new page), Back restored 588; a fresh link click resets to 0. It worked on a client-fetched list because the skeleton grid holds the same height while the data loads. Related gotcha fixed in 5.4: filter changes would also scroll to top, hence `preventScrollReset` there.
- Stretch (`useBlocker`) skipped.

## 5.7 404, errors and error boundaries

- Boundary hierarchy (innermost wins; a boundary catches errors from its own route and everything below it): `routes/product-detail.tsx` and `routes/category.tsx` (`ErrorBoundary` -> `RouteErrorView`, so the header/footer stay) -> `routes/account/layout.tsx` (draws its own sidebar around the error) -> `routes/shell.tsx` (redraws `Header`/`Footer` around the error) -> `root.tsx` (no header, no providers: the last line of defence). Widget-level React boundaries for things like the review list are Stage 12.
- Shared view `components/common/RouteErrorView.tsx` splits "not found" (an unmatched URL is a 404 route error response, a missing product/category is a thrown `NotFoundError` from `lib/notFound.ts`) from "everything else". Not found -> `NotFoundPage`: `<h1>404: ...`, a GET `<Form>` search to `/products?search=`, popular categories from `GET /categories`, home link. Other errors -> "Something went wrong", `role="alert"`, Try again (reload) + home link; only in `import.meta.env.DEV` it also shows the message and stack. Both call `reportError()` (`lib/report.ts`, the one place Sentry plugs in in Stage 14; stretch done).
- The PDP and the category page now THROW `NotFoundError` during render when the API answers 404 (it was an in-page state in 5.3), which is why the boundary and not the page decides how a 404 looks. A static SPA host answers HTTP 200 for every URL, so "404 status semantics" exists only in the UI; real 404 statuses come with SSR (Stage 14 deep dive).
- Verified in the browser (dev server): `/nope/zzz`, `/p/nope-nope`, `/c/nope` each show the 404 page with the header, footer, search box and 8 popular categories; on `/account/profile`, clicking the dev "Throw error" button renders "Something went wrong" + dev detail + stack inside the account content area with the account sidebar, header and footer still there. `DevThrowButton` throws in render after a `setState` because errors thrown inside an event handler are NOT caught by error boundaries.
- Not verified: the `shell.tsx` and root boundaries firing (nothing in the current tree can make the header or shell crash on demand). Production "no stack traces" is checked in 5.9 with a production build.

## 5.8 Page titles, meta, breadcrumbs

- Every route module exports `meta` (`pageTitle("Cart")` -> `"Cart | ShopSphere"`, home/products also a description); `root.tsx` has a fallback `meta` for routes that export none (the leaf's meta wins, parents are not merged). Titles that need data (`"Google F14 Smartphone 5G | ShopSphere"`) come from `hooks/useDocumentTitle`: the route's `meta` gives the generic title and the page refines it after the fetch (SPA mode has no loader data in `meta`).

## 6.1 HTTP in depth

- `docs/api-notes.md` is the table of every B0 and B2 endpoint, verified with `curl -i` (status, error envelope, rate-limit headers). Things I only learned by calling the API: unknown ROUTES and unknown RESOURCES share `NOT_FOUND`; bad JSON is 400 `BAD_REQUEST` while a bad field is 422; `forgot-password` answers 200 for unknown emails on purpose; the 429 comes from a per-IP counter that ALL `/auth/*` calls share (my probing used it up), and it resets when the backend restarts (in-memory store).
- 403 could not be reproduced: there is no admin-only route yet.
- Idempotency: `DELETE /wishlist/:id` twice gives 204, 204 (the state is the same however often it is sent), so a retry, a double click or a replay is harmless. `POST /wishlist` is idempotent via a unique index + upsert (201 then 200). `POST /addresses` is not (two clicks, two addresses), so the UI has to guard it.
- Stretch (conditional requests): the server sends a weak `ETag` and no `Cache-Control`; `If-None-Match` gives a 304 with an empty body. It saves bytes, not server work: Express builds the whole response before comparing the hash.

## 6.2 The API client layer

- `lib/api/client.ts` exports `api<T>(path, { method, query, body, signal, schema, auth, timeoutMs })` (the old `request` was renamed; the paginated variants are `apiPaginated` / `apiPaginatedWithMeta`) plus `configureApi({ getAccessToken, onUnauthorized })`. `lib/api/getJson.ts` is now the only file that calls `fetch`; `grep -rn "fetch(" app` proves it.
- Error model: a 4xx/5xx with the envelope, a non-JSON body (HTML 502), a dead server (`NETWORK_ERROR`, friendly message), our own 10 s deadline (`TIMEOUT`) all become `ApiError` (`isNetwork`, `isTimeout`, `isValidation`, `fieldErrors`). The CALLER'S abort is re-thrown untouched as an `AbortError`, so `useAsyncResource` and friends can ignore it instead of toasting.
- The deadline is `AbortSignal.timeout(10_000)` combined with the caller's signal through `AbortSignal.any`. To tell "I aborted" from "the deadline fired" the code checks `signal?.aborted` on the CALLER's signal first.
- `query` skips `undefined`/`null` and repeats array keys (`?tag=a&tag=b`), as the plan asks. NOTE the backend expects comma lists (`brand=Apple,Samsung`), so catalog keeps building its own string with `toQueryString` (csv) and passes it in the path; `api` appends with `&` when the path already has a `?`.
- `onUnauthorized(error)` may return `true` to say "I have a new token, retry": the client retries ONCE, never in a loop (a refresh that does not help surfaces the 401). Stage 10 only has to fill the two hooks.
- `204` (logout, wishlist delete) resolves to `undefined`; `api<void>` is the default generic.
- `scratch/15-api-client.ts` (in `npm run check:scratch`) starts a `node:http` server and asserts: success, repeated query keys, JSON vs `FormData` bodies, 204, 404 envelope, 422 `fieldErrors`, HTML 502, timeout, abort, token + one retry, and a dead server. It does not need the backend.
- Stretch (axios/ky) skipped: fetch is what the plan recommends and Query only needs a promise-returning function.

## 6.3 CRUD by hand: the address book

- Real token for the stub auth (how the plan's "log in via the stub flow or paste a token" is done): `features/auth/session.ts`. The stub login (`LoginForm`, `DevAuthPanel`) now calls the REAL `POST /auth/login` with the seeded `<role>@shopsphere.dev` account, keeps the access token in a module variable (memory only) and `configureApi({ getAccessToken, onUnauthorized })` is called there at import time (not in an effect: children's effects run BEFORE the parent's, so a child could fire a request before the token hook exists). localStorage only holds a "someone was signed in" hint; after a reload `AuthProvider` restores the token through `POST /auth/refresh` and the httpOnly cookie (checked in the browser: reload on `/account/addresses` stays signed in). A 401 triggers one refresh + one retry; if the refresh fails the session is cleared everywhere. Stage 10 replaces `loginAsDevRole` with the real forms.
- Gotcha found while building it: refresh-token ROTATION. React StrictMode mounts effects twice in dev, which would send two `/auth/refresh` calls; the second would present an already-rotated cookie and the backend treats that as theft (`REFRESH_REUSE`, revokes the family). `refreshSession()` shares ONE in-flight promise. Network tab shows a single refresh per reload.
- `useAddresses()` returns `{ state, pending, rowErrors, create, update, remove, setDefault, reload }`. State is a reducer; `pending` is per row (`{ [id]: "update" | "remove" | "default" }`, plus `"new"` for the add dialog), so other rows stay usable while one is busy. The double-submit guard is a ref (a `Set` of busy keys): two clicks in the same tick both read the same STALE state, but they read the same ref. Verified in the browser: two synchronous clicks on "Add address" produced ONE `POST`.
- Refetch vs patch, chosen per operation: create refetches (the server decides order and whether the new row became default); update, set-default and delete PATCH the local list from the response (`DELETE` returns `newDefaultId`, so the UI promotes the same row the server did). Trade-off: patching saves a round trip and keeps focus/scroll but copies server rules into the client; refetching is always correct but slower and flashes unless the stale list stays visible (it does). Failures never touch the list, so there is nothing to roll back.
- Backend rule for deleting the default: auto-promote the newest remaining address. The confirm dialog says so, and the row is promoted from `newDefaultId` (checked: delete default left 2 cards, exactly one "Default").
- Server errors are inline: the API's 422 `details` become `ApiError.fieldErrors`, shown under the field (`193101` gives "We do not deliver to this pincode yet" under Pincode; the dialog stays open). Non-field errors (network, 409 limit) appear in a `role="alert"` box. Network tab per action: create = POST + GET, update = PATCH, default = POST, delete = DELETE. One request each (plus the one refetch after create).
- shadcn `dialog`, `alert-dialog`, `sonner`, `skeleton` added (`from "cn"` fixed to `@/lib/utils`; `sonner` pulls `next-themes`, harmless without a provider). The form is deliberately plain (`useState` object, string fields): the pain (no touched/dirty state, manual `aria-invalid` wiring, copying server errors by hand) is what Stage 7 replaces.
- Stretch (optimistic delete with rollback) skipped. Why it would be fiddly: removing a row, then re-inserting at the SAME position after a failure, while another action may have changed the list in between.

## 6.4 Wishlist toggle: the shared-state problem

- `features/wishlist`: `WishlistProvider` (mounted in `root.tsx` inside `AuthProvider`) holds ONE `Set<productId>` loaded once per signed-in user from `GET /wishlist/ids`. `useWishlist()` gives `{ status, count, isWishlisted, isPending, toggle }`. `WishlistHeart` (card and PDP) and `WishlistLink` (header count) read the same Set, so toggling a card heart updates the PDP heart and the count with no request (checked in the browser: header went "3 items" to "4 items" instantly, one `POST /wishlist`, then back with one `DELETE`).
- Concurrency decision: while a product has a request in flight, further toggles for THAT product are ignored (ref-guarded, hearts get `aria-busy`/`aria-disabled`). Alternatives: queue (the user clicked twice, so they want it back where it was: two requests, both sent in order) or last-write-wins (needs care to not send a stale one). I chose "ignore" because the client then never has two opposite requests racing and a rollback only ever undoes ONE change; other products stay usable. Double synchronous click on a heart produced a single `POST`.
- Failure: stopped the backend, clicked a heart: the heart filled, the request failed, the heart un-filled again and a toast "Could not save it to your wishlist / Cannot reach the server..." appeared; the count returned to 3.
- Heart behaviour: signed-out users are sent to `/login` with `state.from` (they come back after login); until the ids have loaded the heart is inert. `aria-disabled` instead of `disabled` keeps keyboard focus on the heart while it saves.
- Dependency cycle avoided: catalog's `ProductCard` imports `WishlistHeart` from `@/features/wishlist`, so the wishlist feature must NOT import catalog. Consequences: the wishlist list schema (card shape + `wishlistedAt`) is declared in the wishlist feature instead of extending catalog's `productSchema`, and the `/wishlist` page is composed in `routes/wishlist.tsx` (route imports both `useWishlistProducts` and catalog's `ProductGrid`).
- The `/wishlist` grid filters the fetched list through the shared Set, which makes remove instant and a failed remove reappear.
- Dev-server gotcha: `lsof -ti:4000 | xargs kill` also matches CLIENT connections (the browser pane), so use `lsof -ti:4000 -sTCP:LISTEN` to stop only the server.

- Layout shift: skeleton region 1917px vs loaded grid 2073px (titles wrap to two lines), measured CLS across the swap 0.0002 (PerformanceObserver `layout-shift`); the shift only matters when something below sits in the viewport, and here the footer is far below. Making the skeleton card the same height as a 2-line-title card would remove the rest.

## 6.6 Pagination vs infinite scroll

- `/products?mode=more` (the `mode` filter is parsed/serialised with the other URL filters; default `pages` is omitted from the URL; a toolbar button switches). Classic pagination stays the default. Only the ACTIVE mode makes requests: `useProducts(query, enabled)` and `useInfiniteProducts(query, enabled)` both take `enabled` (added a third `enabled` argument to `useAsyncResource`), so switching mode does not fire a hidden page-1 request.
- `useInfiniteProducts`: a reducer whose state belongs to ONE filter set (`key` = query string without `page`). Every response is tagged with the key and the page it answers, and the reducer ignores anything that no longer matches the current key/`nextPage`. Dedupe by `_id` when appending. A page-N failure sets `error-more` and keeps pages 1..N-1 on screen with an inline `ErrorState` + Retry that asks for page N only; a page-1 failure shows the full error state. A `busy` ref blocks a second request while one is in flight.
- `LoadMoreSentinel`: `IntersectionObserver` with 400px `rootMargin`, created in an effect and disconnected in the cleanup; the callback is an Effect Event (a new function each render must not recreate the observer). `itemCount` is a dependency ON PURPOSE: after a page is appended the sentinel can still be visible, and an observer only reports CHANGES, so a fresh observer is needed to report "still visible" and chain the next load. The sentinel is a 1px non-focusable `div`; the visible "Load more" button is the fallback for keyboard users, so the footer stays reachable.
- Verified in the browser with `fetch` wrapped to log URLs: 40 aggressive scroll-to-bottom calls loaded pages 2..11 each exactly ONCE, in order (132 cards, 132 unique ids); a brand with 12 products ended with "You've seen it all (12 products)" and later scrolling made 0 requests (observer not mounted); starting page 2 (1.5 s delay) and then switching to `brand=Samsung` left only Samsung cards (6), no mixing, the old request aborted; a forced network failure on page 3 kept 24 cards, showed an inline error, and Retry added page 3 (36 cards).
- Performance note for Stage 13: 36 cards = 897 DOM nodes (about 20 per card), so a 308-product scroll is ~7,000 nodes and growing: virtualization candidate. Back button does not restore the loaded pages (stretch skipped: it would need `sessionStorage` keyed by URL).
