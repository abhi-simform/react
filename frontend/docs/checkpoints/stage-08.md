# Stage 8 checkpoint: model answers

**1. Where should each live: selected variant, cart lines of a logged-in user, drawer-open flag, filters, current user, theme?**
Selected variant: local `useState` in the buy box (only it reads it; `key={slug}` resets it; the chosen variant and price are DERIVED from it). Cart lines of a logged-in user: server cache (TanStack Query in Stage 9, behind one cart facade hook); the guest cart is a persisted Zustand store because there is no server to own it. Drawer-open flag: global client state (Zustand UI flag, not persisted), because distant components (a toast action on a product card) must open it. Filters: the URL (shareable, Back works, no `useState` copy). Current user: Context (`AuthProvider`: low-frequency, read everywhere; the token stays in memory, only a "session exists" hint is persisted). Theme: Context + `localStorage` for the choice, and the applied light/dark is derived from the choice and the OS setting.

**2. Why does a Context value change re-render all consumers and how do selectors in Zustand avoid it?**
React re-renders every component that calls `useContext(X)` whenever the provider's `value` is not `Object.is`-equal to the previous one; there is no way to subscribe to "part" of a context value, and an inline `value={{...}}` is a new object on every provider render. I measured 50 consumers: inline value +50 renders per tick AND per unrelated provider render, memoized value +50 per tick but 0 for unrelated renders, split state/actions contexts 0 for consumers that only need actions. Zustand keeps state outside React and every `useStore(selector)` subscribes through `useSyncExternalStore`: on each store change it runs the selector and re-renders only if the SELECTED value changed (`Object.is`; `useShallow` for small objects/arrays). In the lab, toggling the drawer flag re-rendered the `useCartStore()` (no selector) badge every time and the `s => s.lines.length` badge never.

**3. Why are cart totals never stored?**
They are a pure function of lines (plus coupon and shipping rules). A stored copy is a second source of truth that every action (add, quantity, remove, restore, undo, a rule change, a cross-tab rehydrate) must remember to update; one missed path shows a wrong price. Deriving (`useMemo(() => computeTotals(lines), [lines])`) makes inconsistency impossible and costs a few microseconds. Same reasoning for the line count, free-shipping progress, the applied theme and the compare table rows.

**4. What is the rule of thumb for lifting state vs using a store?**
Keep state as close as possible to where it is used. If two siblings need it, lift it to their nearest common parent; if the parent is far, try composition first (pass the element as `children`/a slot so the middle layers never see the data). Reach for a store only when many DISTANT components share CLIENT-only state, that state is not server data, and it has to survive navigation (cart drawer, compare list, guest cart). Context is for low-frequency delivery (user, theme), not for fast-changing values.

**5. What is wrong with `const { lines, drawerOpen } = useCartStore()`?**
No selector means the component subscribes to the WHOLE store: it re-renders on every change of any field, including ones it does not render (`drawerOpen` toggling re-renders a badge that only shows the count). Select what you render: `useCartStore(s => s.lines.length)`, and for several fields `useShallow`. Returning a NEW object from the selector (`s => ({ a: s.a })`) is worse: it is never `Object.is`-equal, so React sees a changed snapshot every read and loops ("getSnapshot should be cached", "Maximum update depth exceeded"); I kept that broken selector in `scratch/zustand/BrokenSelector.tsx` (`/dev/state?broken=1`). Actions can be read with `useCartStore.getState()` in handlers, which needs no subscription at all.
