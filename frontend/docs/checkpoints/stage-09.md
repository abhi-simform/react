# Stage 9 checkpoint: model answers

**1. What is the difference between `staleTime` and `gcTime`?**
`staleTime` decides WHETHER cached data is still trusted: while it is fresh, mounting, window focus and reconnect do not refetch it (default 0: stale at once, so every new observer refetches). `gcTime` decides HOW LONG data with no observers stays in the cache; it starts counting when the last component using the key unmounts (default 5 minutes), after which the entry is deleted and the next visit is a cold load. Fresh vs stale is about refetching; active vs inactive is about memory. Mine: categories 30 min, lists 2 min, PDP 20 s, cart 5 s, with `gcTime` 5 min everywhere (docs/query-policy.md).

**2. What does `isPending` mean vs `isFetching`? What is `fetchStatus`?**
`status` describes the DATA: `pending` (none yet), `success`, `error`. `fetchStatus` describes the REQUEST: `fetching`, `paused` (wants to fetch but offline) or `idle`. `isPending` = no data for this key yet (first visit to a filter: skeleton); `isFetching` = a request is in flight, first or background (focus refetch on a visible list, paging with `keepPreviousData`: data on screen, `isFetching` true). `isLoading = isFetching && isPending`. A disabled query (`enabled: false`) is `pending` + `idle`: no data and doing nothing, which my dependent reviews/similar sections show as "Waiting for the product...".

**3. Walk through an optimistic update step by step, including rollback.**
Wishlist heart. `onMutate`: `await cancelQueries(wishlistKeys.all)` (an in-flight refetch could resolve after my optimistic write and put the old answer back), snapshot what I will change (the open lists), write the new value with `setQueryData` as a NEW array (never mutate cached data), and return the snapshot as `context`. Then the request runs. `onError(err, vars, context)`: apply the inverse for that one product (not a whole-ids snapshot: it would also revert hearts toggled meanwhile), restore the lists, show ONE toast. `onSettled` (success or failure): invalidate the family so the cache re-syncs with the server. UI-based alternative: render from `mutation.variables` while pending, no cache surgery; right for one toggle, wrong when many components read the same data (header count, grid, PDP). Cart quantity adds a 400 ms per-line debounce: the cache changes at once, one PATCH carries the last value, a failure rolls the line back to the value before the burst, and a response is written only if it is the last cart mutation (last response wins).

**4. Why are query keys the dependency array, and how do you design them for invalidation?**
Query re-runs `queryFn` when the key's hash changes, exactly like `useEffect` deps: anything the request depends on must be in the key (filters, slug, page, owner). Keys are hashed with sorted object keys, so they must be plain JSON. Design them hierarchically, most general to most specific: `["products", "list", filters]`, `["products", "detail", slug]`: then `invalidateQueries({ queryKey: ["products", "list"] })` hits every list and no detail, `["addresses"]` hits the whole family, and a mutation can name precisely what changed (a new review invalidates `reviewKeys.forProduct(id)` and that product's detail, not every list). Build them in factories (`lib/queryKeys.ts`) plus `queryOptions` (`productQueries.detail(slug)`) so hooks, prefetch and tests share one definition and no component writes an inline key. User-scoped data needs an owner in the key or an explicit reset on sign-out (`SessionCacheSync`).

**5. Why is the cart a hybrid (guest vs user) and how does the facade hide it?**
A user's cart must follow them across devices (server, JWT); a guest has no account but still needs a cart that survives a reload. B3 gives guests a server cart too, identified by a random token in `localStorage` (`x-cart-token`; it names a cart, it is not a credential), so both are the same Query with a different OWNER. `useCart()` resolves the owner (signed in -> Bearer, else the token), keys the cache by owner (the two never share an entry), and returns the same `{ lines, totals, add, setQty, remove, saveForLater, moveToCart }` for both; components never branch on it. On login `POST /cart/merge` folds the guest cart into the user's (quantities add, capped by stock, reported back) and the token is dropped. One source of truth at a time: the Zustand lines were deleted; Zustand only keeps the drawer flag and 409 line messages.

**6. When should you not use Query?**
For anything that is not a cache of server data: form drafts (React Hook Form), UI toggles (drawer open, dialog open, selected tab/variant: local state, Zustand for distant sharing, the URL for shareable ones), derived values (totals), and browser APIs (online status, media queries: external stores). Also for the auth session bootstrapping in this app (a one-shot restore through a cookie, reworked in Stage 10) and one-shot imperative syncs (the cart merge). Query also does not replace thinking about server rules: optimistic patches that copy server logic (the cart's `recount`) can drift.

**7. How does `placeholderData: keepPreviousData` change UX versus `initialData`?**
`keepPreviousData` shows the PREVIOUS key's data (dimmed, with an updating indicator) while the new key loads: the grid does not collapse to a skeleton when paging or filtering; the data is not written to the cache for the new key and a request is always made. `placeholderData: () => fromAList` does the same for a detail page (basic fields at once). `initialData` is real cache content for that key: it counts as data, obeys `staleTime` (fresh initial data means NO request), and shows as `success`, not as a placeholder; right when the data is trustworthy and complete (e.g. hydrated from a server render), risky when it is partial (a list item standing in for a detail would be treated as final).
