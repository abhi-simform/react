# Stage 4 checkpoint: model answers

1. **"An effect synchronizes with an external system".** An effect describes how to START syncing a component with something outside React's render, how to STOP (cleanup) and which values it depends on. ShopSphere examples: (a) `GET /products` for the current page (`useProducts`), (b) the shared `setInterval` behind `useCountdown`/`useNow`, (c) `document.addEventListener("keydown")` for the `/` shortcut, also `localStorage` writes for recently viewed and `matchMedia` subscriptions. Non-example: filtering the visible products from `products` + `filters`, or computing `total = qty * price`: no external system, so compute during render (the effect version rendered extra commits and showed wrong frames in 4.1 and Bug 5).
2. **Why it runs twice in dev.** StrictMode mounts, unmounts and mounts again every component once, so each effect runs setup, cleanup, setup. It exposes effects whose cleanup is missing or asymmetric: a leaked listener (Bug 2: 16 added vs 7 removed), a timer that keeps running, a request whose late response overwrites state. If the app is correct after the double run, cleanup is correct. Production runs it once.
3. **Two overlapping search requests.** Without abort: t0 send "watch" (slow), t1 send "cream" (fast), t2 "cream" answers and the UI shows cream, t3 "watch" answers late and the UI shows watch: wrong (observed `Input: cream / showing: watch`). With AbortController: at t1 the cleanup of the first effect calls `abort()`, the first request is `(canceled)` and its promise rejects with `AbortError`, which is ignored; only "cream" ever updates the UI. (`AbortError` is not a failure: we caused it on purpose.)
4. **Debounce a value, and why both debounce and cancellation.** A debounced VALUE (`useDebounce`) is plain state that changes only after a pause, so the request effect that depends on it simply runs less often, with its normal cleanup. Debouncing the request FUNCTION inside a component is recreated each render (the timer never accumulates) and fights stale closures. Debounce reduces how many requests START (typing "iphone" sends one, not six); cancellation guarantees that of the requests that were started, only the latest can update the UI. A request started before the pause can still be overtaken by a slower older one, so you need both.
5. **How `useCountdown` avoids drift; server vs client time.** It never decrements; it stores the target timestamp and computes `end - (now + serverOffsetMs)` from the clock on every tick, so late or throttled ticks (background tabs) still show the right time, and the shared `useNow` refreshes on `visibilitychange`. `serverOffsetMs = serverTime - clientTime` (measured once): if the client clock is 5 minutes fast, the offset is -5 min, so the countdown still ends at the SERVER's `endsAt`. Stage 4 uses a stub offset of 0 because the time/deals endpoint (B4) does not exist yet.
6. **When is `useMemo` useless, and `memo`?** `useMemo` is useless for cheap computations (a trivial product benchmark was ~5x slower with the memo bookkeeping; filtering 1,000 products costs ~0.4 ms) and when its result is not needed for referential stability. `memo` is useless when a prop changes every render, typically an inline `onClick={() => ...}` or an object/array literal (the "memo-inline" mode rendered 200 rows exactly like plain), or when the component re-renders anyway because its props really change. It pays off with a stable callback (`useCallback`) under a parent that re-renders for unrelated reasons (200 renders became 0).
7. **Rules of Hooks and why.** Call hooks only at the top level of a component or custom hook (not in conditions, loops, nested functions, after an early return) and only from React functions. React keeps hook state in an ordered list per component and identifies a hook only by its call position; a changed order shifts every later hook onto the wrong slot (observed: "Rendered more hooks than during the previous render"). The `rules-of-hooks` lint rule enforces it statically.
