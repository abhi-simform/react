# Stage 14 checkpoint: explain it without notes

1. **From `git push` to a changed page on the public URL.** `git push` to GitHub -> GitHub Actions starts the workflow (checkout, `npm ci` from the npm cache, format/lint/typecheck/tests/build, e2e against MongoDB + the API + the production build, Docker image build) -> on merge to the main branch the host's Git integration notices the commit: Vercel/Netlify clones the repo, runs `npm run build` with the project's `VITE_*` variables (Vite inlines them), uploads the static files to its CDN, and `index.html`/`sw.js` are revalidated while hashed assets are new URLs; if `SENTRY_AUTH_TOKEN` is set the build uploads source maps to Sentry under the commit SHA and deletes them from the output -> the CDN's DNS name (`shop.example.com`, a CNAME managed at the DNS provider, certificate from the host) serves the new files -> the browser fetches `index.html` (no-cache), sees new hashes, downloads them; the service worker installs the new version and the user gets the "new version available" toast. The API takes the same route through Render/Railway (build the Dockerfile, health check `/api/v1/health`, switch traffic) talking to MongoDB Atlas.
2. **Why a cross-site refresh cookie fails, and two fixes.** The cookie belongs to the API's site; a page on another registrable domain (`*.vercel.app` calling `*.onrender.com`) makes the refresh `fetch` cross-site. With `SameSite=Lax` the browser does not attach the cookie to a cross-site request at all, so `/auth/refresh` answers 401 and every reload logs the user out; `SameSite=None; Secure` is allowed but is a third-party cookie that Safari and Firefox block. Fixes: (1) put the frontend and API on sibling subdomains of one registrable domain (`shop.` + `api.example.com`: same-site, `Lax` works), (2) proxy `/api` through the frontend host so the browser sees one origin. (Reproduced locally with `127.0.0.1` vs `localhost`: login 200, refresh 401 `NO_REFRESH_TOKEN`; with `None; Secure` refresh 200.)
3. **What Sentry needs for a readable stack trace.** The source maps of exactly the build that is running, uploaded before the first event arrives and matched by release (the git SHA in `VITE_RELEASE`, the same value in the SDK's `release` and the upload; modern plugins also inject a debug id into each file). The maps must not be public (hidden maps, deleted after upload), and the file URLs in the stack must match what was uploaded.
4. **What `ssr: true` changes for `localStorage` code.** Render also runs on the server where `window`, `localStorage`, `matchMedia` and `IntersectionObserver` do not exist, so none of them may be read during render: a crash on the server, or a different first render on the client = a hydration mismatch (and React does not patch mismatched attributes such as a `<select>`'s value). Read browser state in an effect (after hydration), or with `useSyncExternalStore` and a server snapshot equal to what the server rendered; mark deliberate differences with `suppressHydrationWarning` on that one element; keep a module-level `QueryClient` out of the server (per-request clients).
5. **Loaders and actions vs Query.** A `loader` is a route's server-side (or client-side with `clientLoader`) function that runs in parallel before the route renders, its data typed into the component; an `action` handles a `<Form>` POST (works without JS) and revalidates the loaders afterwards. They give data by route and navigation; Query gives a cache keyed by data with freshness, de-duplication, background refetch, optimistic updates and cache sharing between routes. They compose: seed Query with loader data via `initialData` (+ `initialDataUpdatedAt`) so there is no second fetch; keep Query for interactive and user-specific data.
6. **Rolling back.** Frontend: promote the previous deployment (Vercel "Promote", Netlify "Publish deploy") or run the previous image tag: instant, no rebuild; the service worker file is `no-cache` so clients update within a load. Backend: the host's "Rollback" to the previous deploy; code only, so migrations must stay compatible for one release. Data: restore a dump into a NEW database and switch `MONGODB_URI`.
7. **Why a webhook URL is a production concern.** The payment provider calls the server from the public internet when a payment settles or fails, even if the customer closed the tab. `localhost` is unreachable, so locally a mock gateway posts to itself; in production the URL must be public, HTTPS, stable, verified by signature over the raw body, and idempotent because the provider retries. Registering it is a dashboard step per environment (test vs live), and the API's `RAZORPAY_WEBHOOK_SECRET` must match.
