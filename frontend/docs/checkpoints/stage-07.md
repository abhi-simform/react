# Stage 7 checkpoint: model answers

**1. Why is RHF fast, and what is the cost of `watch("field")` at the form root?**
RHF keeps values in the DOM and in refs (inputs are uncontrolled): `register` gives each input a ref and `onChange`/`onBlur` handlers that write to RHF's internal store, so typing does not call `setState` and the form component does not re-render. It re-renders only for what you subscribe to (`formState.errors`, `isSubmitting`, `useWatch` in a child). `watch("field")` in the component that calls `useForm` subscribes THAT component, so the whole form (every field below it) re-renders on every keystroke of that field. I measured it in `/dev/forms`: 5 keystrokes gave 6 commits per sibling field for a plain `useState` form, 2 (mount only) for RHF, 2 with `useWatch` in a child, and 7 with `watch("name")` at the root. Use `useWatch` in a leaf, or `getValues()` in a handler.

**2. What are `z.input` and `z.output`, and when do they differ?**
`z.input<S>` is what the schema accepts (the form fields), `z.output<S>` is what `parse` returns (what `handleSubmit` hands you). They differ whenever the schema transforms: `z.coerce.number()` takes `unknown` (the radio's string "4") and returns a `number`; `.transform` (`line2: ""` becomes `undefined`), `.default()`, `.trim()`/`.toLowerCase()` outputs, or `.pipe`. So `useForm<z.input<S>, unknown, z.output<S>>({ resolver: zodResolver(S) })`: values in the form have the input type, `onSubmit` receives the output type. Pitfall: `z.coerce.number()` turns `""` into `0`; put `.min(1)` on a string first (`z.string().min(1).pipe(z.coerce.number())`).

**3. How do you show a server "email already exists" error, and why must the client never be the only validator?**
Catch the `ApiError`, and map by code/path: `setError("email", { type: "server", message }, { shouldFocus: true })` for `EMAIL_TAKEN` (409) and for each `details[{path,message}]` of a 422; `setError("root.server", ...)` for form-level problems (network, 5xx) with a retry. Mark the field `aria-invalid`, link the message with `aria-describedby`, `role="alert"`. The client cannot be the only validator because anyone can call the API directly or edit the bundle, rules drift between client and server, and some rules only the server can know (uniqueness, serviceability, stock, permissions). Client validation is feedback; the server decides (I checked: an unserviceable pincode that slips past the client still gets a 422 on `POST /addresses`, shown under the pincode field).

**4. Why use `field.id` as a key in `useFieldArray`?**
Array rows have no identity in the data; RHF generates a stable `id` per row (`fields[i].id`) and keeps it through `append`/`remove`/`move`. With `key={index}` React reuses the DOM node of position i for whatever row now sits at i: focus, selection, IME state and any child component's own state stay on the node while the data moves, and RHF's own docs warn about it. In my run plain `register`ed text inputs still showed the right values with index keys (RHF rewrites DOM values by name), so the failure is subtler than "scrambled values", but the id is the only correct key.

**5. How do you prevent stale async validation results from appearing?**
Layered: validate the format locally and instantly; debounce before any request; abort the previous request when the value changes (`AbortController`, which `useFetch` does on key change); store each result with the key it answers and ignore results for another key (`useFetch`'s settled key, plus an explicit `data.pincode === value` check); remember that the answer is advisory and the server re-validates on submit. Demonstrated by delaying `GET /pincodes/560001` by 2.5 s, typing `790001` after it: the screen kept the 790001 answer when the old response arrived.

**6. What leaks if you forget `URL.revokeObjectURL`?**
The blob URL is a strong reference to the File's data until it is revoked or the document unloads, so each preview shown and dropped keeps up to 2 MB alive for the whole session (a long-lived SPA grows). I made the URL reference-counted per file (`useObjectUrl`) and verified with a dev counter that it returns to 0 on remove, on submit/reset and on navigating away.

**7. How does a multi-step form survive refresh and Back?**
Each step is a route (a URL), the whole flow shares ONE form (`FormProvider` in the layout route, so unmounted steps keep their values), the draft is written to `sessionStorage` on every change (per user id) and restored into `defaultValues` once, validation is per step (`trigger(stepFields)` against `schema.pick`), and a guard sends a deep link to the first incomplete step. Back/Forward are the browser's history between step URLs (steps push history entries), and refresh restores the draft. Finishing clears the draft.
