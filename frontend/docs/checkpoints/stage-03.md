# Stage 3 checkpoint: model answers

1. **What does React use `key` for, and what breaks with index keys?** `key` is the identity React uses to match an element in the new render with an element in the previous one among siblings. Matched elements keep their state and DOM; unmatched ones are created or destroyed. With index keys, identity is "position", so when the list is sorted, filtered or has an insert, the instance at position 0 is reused for whatever product is now first: local state (the `liked` heart, a typed quantity, a focused input) stays at the position and ends up on the wrong product. Reproduced on `/scratch/grid`: liked card 1, sorted by price, the heart stayed on slot 1 (a different product). Stable ids (`product._id`) fix it. Index keys are fine only for static lists that never reorder.
2. **Three pieces of PDP state that should be derived.** The selected `Variant` object (derive it from `variants` + the selected attribute values), the displayed price/MRP/discount (from the variant), and the stock message / "can add to cart" flag. Also the shown quantity (`Math.min(qty, stock)`), the next image to preload and the "2 of 4" label (from the gallery index). The stored state is only the user's choices: attribute values, index, wished quantity.
3. **Resetting state when a prop identity changes, and why not an effect.** Render the component with `key={product.slug}` (`<ProductDetailView key={slug} .../>`): a new key unmounts the old instance and mounts a fresh one, resetting all of its state and its children's state at once. An effect (`useEffect(() => setIndex(0), [slug])`) runs after the new product has already been painted with the old state (a flash of wrong UI), costs a second render, and must be repeated for every state variable.
4. **Why a card must not nest a `<button>` in an `<a>`.** Interactive content inside an `<a>` is invalid HTML; the click target is ambiguous (does the click navigate or toggle?), keyboard and screen readers get two nested tab stops/roles, and browsers handle it inconsistently. Pattern used: the title is the only link, stretched across the card with `after:absolute after:inset-0`, and the heart and "Add to cart" buttons are siblings with `relative z-10`.
5. **Controlled vs uncontrolled input.** Controlled (`value` + `onChange`): one source of truth, so you can validate, format, clamp, count characters and derive UI on every keystroke; cost: a re-render per keystroke and state plumbing for every field. Uncontrolled (DOM owns the value, read via ref or `FormData` on submit): less code and fewer renders, works well with libraries like React Hook Form; cost: you cannot react to each change or force a value without imperative code.
