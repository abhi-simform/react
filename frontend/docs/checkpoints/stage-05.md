# Stage 5 checkpoint: model answers

1. **RR's three modes, and which are we in?** Declarative (`<BrowserRouter>` + `<Routes>`/`<Route>` JSX, no data APIs), data (`createBrowserRouter` object tree + `RouterProvider`, loaders/actions/`errorElement`/`useNavigation`), framework (Vite plugin: `routes.ts` config, generated `+types`, per-route code splitting, `meta`/`handle`/`ErrorBoundary` exports, optional SSR). We are in framework mode with `ssr: false`: a static SPA (`build/client` + `index.html`, no server at runtime) written with the declarative-style hooks and components. With `ssr: true` the same route tree would also render on a server per request: route modules must not touch `window`/`localStorage` during render, `loader` (server) vs `clientLoader` (browser) becomes a real choice, `meta` can use loader data so titles and tags are in the HTML crawlers receive, and a Node server is needed at runtime.
2. **URL vs `useState`.** In the URL (shareable, bookmarkable, survives refresh, Back/Forward work): listing filters (`brand`, `minPrice`, `minRating`, `inStock`), `sort`, `page`/`view`; the category (`/c/mobiles`); the product (`/p/:slug`); the selected checkout step; search term (`?search=`). In `useState` (ephemeral UI): whether the mobile filter sheet or the mega menu is open, the half-typed price in the input before it is committed (a draft, committed to the URL after 500 ms), the hovered/liked heart, an in-progress review textarea. Rule of thumb: if a user would be annoyed that a refresh or a pasted link lost it, it is URL state; derive it from `useSearchParams`, never copy it into state.
3. **Why a client guard is not a security boundary.** The guard is JavaScript in the user's browser: anyone can edit `localStorage`, change the bundle, or call the API with curl and skip the UI entirely. The guard only avoids showing pages that would fail (UX). The API must authorise every request (401 without a valid token, 403 for the wrong role), and the UI must still handle those responses.
4. **Back with a slider/typing that changes the URL 40 times.** Use `replace` for transient changes and `push` for discrete ones: typing/dragging updates a local draft, debounces, and commits ONE `setSearchParams(..., { replace: true })` (we measured RR's `history.state.idx` unchanged after five quick keystrokes and one request); checkboxes, sort, bar clicks and page changes push, so Back undoes one meaningful step. Also `preventScrollReset` so filtering does not jump to the top.
5. **Error boundary hierarchy.** A route's `ErrorBoundary` catches render errors in that route and below and renders in that route's slot, so parents (header, footer, account sidebar) stay. Boundaries at several levels (route, layout, root) contain the blast radius: an error in the account profile shows inside the account layout's content area; an error that escapes everything reaches the shell boundary (header/footer redrawn) and finally the root. For a widget such as the review list, a React-level boundary around just that widget (Stage 12) lets the rest of the PDP render; without it the error would reach the route boundary and replace the whole PDP content. Errors thrown in event handlers or async code are not caught by boundaries.
6. **Why `ScrollRestoration`, and the a11y problem of client routing.** A SPA swaps content without a page load, so the browser's built-in scroll restoration (Back returns to your place) and reset (new page starts at the top) do not apply; `ScrollRestoration` stores/restores scroll per history entry (we saw 588 px restored on Back, 0 on a new navigation). The a11y problem: no page load means focus stays on the clicked link (or on nothing) and screen readers announce nothing, so users do not know the page changed. Fix: after a pathname change move focus to the new `<h1>` and write the title in a polite live region (`useRouteFocus`), keep a skip link, and unique `<title>`s.
