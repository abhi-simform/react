# Stage 11 checkpoint: model answers

**1. Why can the Razorpay `handler` callback not be trusted as proof of payment? What is?**
The handler runs in the browser, which the user controls: anyone can call it, or fake the request their app sends afterwards, with made-up ids. It also may never run (tab closed, network lost after the money moved). The proof is a signature the SERVER verifies: Razorpay signs `order_id|payment_id` with the key secret (HMAC-SHA256) and only the server knows that secret, so `POST /payments/verify` recomputes it (constant-time compare) and checks the amount and the provider order id belong to OUR order. Even better, the signed webhook from Razorpay to the server is the source of truth (idempotent, so webhook and verify can both arrive in any order and exactly one marks the order paid). The UI therefore shows "paid" only from server state (polling or a socket event), never from the callback itself.

**2. How does an idempotency key prevent double orders on retry?**
The client creates one key per checkout attempt (`crypto.randomUUID()`, persisted so a reload reuses it) and sends it as `Idempotency-Key`. The server stores it on the order under a unique index (user, key) and a fingerprint of the request. A retry (lost response, double click, two tabs) with the same key finds the first order and returns it (`Idempotent-Replayed: true`) instead of creating another; two parallel requests race on the unique index and the loser returns the winner's order. The same key with a DIFFERENT request is `422 IDEMPOTENCY_KEY_REUSED`, because that is a client bug. A new checkout attempt gets a new key.

**3. Which states allow cancel/return and where is that rule enforced (UI and API)?**
Cancel: `pending_payment` and `placed` (before packing). Return: `delivered`, within 7 days of delivery (`returnableUntil`). The rule is a state machine in the API (`TRANSITIONS`, `CANCELLABLE`, `RETURN_WINDOW_DAYS`): every change is a conditional update guarded by the current status, so a stale tab or a double click gets `409 INVALID_TRANSITION` (or `RETURN_WINDOW_CLOSED`) and cancel happens once. The UI repeats the rule only to show the right buttons (`canCancel(status)`, `canReturn(status)` and the server's `returnableUntil`); it is a convenience, and when it is stale (the admin packed the order while the page was open) the optimistic cancel rolls back to the server's status and explains why.

**4. How do socket events, Query cache and polling cooperate without duplication?**
There is one data flow: components read the Query cache. A single `RealtimeSync` listens to the socket and turns each event into a cache update: `order:status` PATCHES the cached order (the timeline moves at once) and then INVALIDATES it, so the server's version replaces the patch and anything the event does not carry arrives in one refetch; `notification:new` sets the unread count, prepends to the dropdown and invalidates the list. Polling is only the fallback: the order query polls only while the socket is not connected (pending payments keep their own short poll, the money path should not depend on a socket). Events are idempotent (a history line is appended only if it is not there), and every RE-connect refetches notifications and orders, because events are not replayed, so a missed one is repaired by a refetch, never by a replay.

**5. Why does the socket auth use a callback, and what happens on token expiry?**
`auth: { token }` would be evaluated once, when the socket is created, so every reconnect would send the first (by now expired) token. `auth: (cb) => cb({ token: currentToken() })` is called on every connection attempt, so a reconnect after a refresh carries the current token. On expiry the handshake is refused with `connect_error` whose `data.code` is `TOKEN_EXPIRED` (or `INVALID_TOKEN`); Socket.io does not retry a refused handshake by itself, so the client refreshes the access token (the same single-flight refresh as HTTP) and calls `connect()` again, at most a few times in a row so a dead session cannot loop. The server also drops a socket when its token expires (`auth:expired` + server disconnect, which Socket.io likewise does not reconnect), so a logged-out or revoked session is cut off within the token lifetime.

**6. How do you merge a guest cart without losing items or exceeding stock?**
After login the client calls `POST /cart/merge {guestToken}` (Bearer required). The server folds the guest cart into the user's cart in ONE transaction and deletes the guest cart, so a retry cannot double the quantities: for the same product the quantities add, capped at `min(stock, 10)`; a new product is copied (with its saved-for-later flag); unavailable or out-of-stock products are skipped. The response is the merged cart plus a report (`merged`, `adjusted` with requested vs applied, `skipped` with reasons). The UI never decides quantities: it shows that report in a toast ("2 items merged, one limited by stock"), offers a retry if the call failed (the guest cart still exists), and refetches the cart, so the shopper learns about every clamp instead of silently losing items.

**7. Walk through the autocomplete request pipeline from keypress to rendered option.**
Keypress -> the controlled input's `term` state -> `useDebounce(normalizeTerm(term), 250)` (trim, collapse spaces, lower case: one normal form is the request and the cache key) -> `useQuery` with key `["search","suggestions",term]`, `enabled` from 2 characters, `placeholderData: keepPreviousData` -> `GET /search/suggest?q=` with the query's `signal` (typing on changes the key, which aborts the previous request; a term seen before is answered from cache) -> the response is validated with Zod -> `buildGroups` (pure: did-you-mean, products, categories, brands, always a "Search for" row, recents when empty) gives stable option ids and destinations -> `SuggestionList` renders a listbox with `<mark>`-highlighted text (split by a helper, no HTML strings) while the input keeps DOM focus and `aria-activedescendant` names the active option (arrow keys move an index over the flat list). Enter on an option navigates (product page, category, brand filter, or `/products?search=`) and stores a search as a recent term (case-insensitive de-duplicated, max 8). `onMouseDown` preventDefault keeps the input focused so `click` (and touch) works before blur closes the list.
