# Stage 2 checkpoint: model answers

1. **Why is `any` contagious? Example.** Anything derived from an `any` is `any`, and `any` is assignable to everything, so the compiler stops checking along the whole chain. `const data = await res.json()` is `any` (lib.dom); `data.items.map(i => i.price * 2)` typechecks even if the server renamed `items`; `i` is `any`, the result array is `any[]`, it flows into props, and a typo like `product.titel` anywhere below compiles. The first sign is `NaN` or a blank card at runtime. `unknown` blocks that: you must narrow (guard or Zod) before touching a field.
2. **`AsyncState<Product[]>` and impossible states.** Four states, one at a time: `idle`, `loading`, `success { data: Product[] }`, `error { error: ApiError }`. `data` exists only in `success` and `error` only in `error`, so it is impossible to be loading and errored at once, to be "success" without data, or to have stale data next to an error flag. The three-boolean version (`isLoading`, `isError`, `data?`) can express `isLoading && isError` and every consumer must guess the priority.
3. **How `assertNever` makes adding `"refunded"` safe.** Each switch ends with `default: return assertNever(status)`, where `status` has been narrowed to the members not yet handled. If a member is missing, the leftover type is not `never`, so the call fails to compile (`'"refunded"' is not assignable to 'never'`) and tsc lists every switch to update (4 of them here). At runtime the same default throws if impossible data arrives.
4. **Why `z.infer` instead of a hand-written interface.** The schema is the single source of truth: the runtime validator and the static type are generated from one definition, so they cannot drift, and a field added to the schema appears in the type automatically. A hand-written interface is a claim the compiler cannot verify against real JSON; a Zod-inferred type is a claim that has been checked at the boundary.
5. **`Pick` vs `Omit` vs `Partial` in ShopSphere.** `Pick<Product, "slug" | "name" | "images" | "price" | "mrp" | "ratingAvg">` keeps only the fields a `ProductCard` needs (`ProductCardData`); `Omit<CartItem, "priceSnapshot">` is a payload without server-owned fields (`CartItemInput`, what the UI sends on add to cart); `Partial<{ page, limit, sort, ... }>` makes everything optional (`ProductQuery`, filters and PATCH bodies like profile updates).
