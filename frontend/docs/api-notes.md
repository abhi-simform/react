# API notes (6.1): verified with real requests

Base `http://localhost:4000/api/v1`. Every row below was exercised with `curl -i` against the running backend (seeded DB, dev customer), not copied from Swagger. "Auth" = needs `Authorization: Bearer <accessToken>`.

Envelope: success `{ success: true, data, meta? }`, failure `{ success: false, error: { code, message, details? } }`. Pagination `meta` sits NEXT to `data` (not inside it): `{ page, limit, total, totalPages, hasNext, hasPrev }`, and `totalPages = max(1, ceil(total / limit))` (e.g. 308 products, `limit=60` gives 6 pages; an empty result still reports `totalPages: 1`).

Observations: the 429 arrived after about 17 attempts in my run because the earlier probing calls to other `/auth/*` routes share the same counter. Rate limiting is in memory, so restarting the backend resets it (I did, and reseeded). A 409 is returned for `EMAIL_TAKEN` and `ADDRESS_LIMIT`: state conflicts the user can fix (see Checkpoint 4 in `checkpoints/stage-06.md`).

## Idempotency

`DELETE /wishlist/:productId` twice: 204 and 204. The end state ("product not in the wishlist") is the same however many times it is sent, so a retry after a timeout, a double click or a service worker replay cannot hurt: that is idempotency (same request N times == once, in terms of server state). `POST /wishlist` is idempotent too (201, then 200, one row: a unique index `(user, product)` plus an upsert). `POST /addresses` is NOT idempotent (two clicks, two addresses; the UI must guard). `DELETE /addresses/:id` is idempotent in state but answers 404 the second time.

## Conditional requests (stretch)

The server sends a weak `ETag` on every JSON response but no `Cache-Control`. `GET /products?limit=1` then the same with `If-None-Match: <etag>` gives `304 Not Modified` with an empty body. What it buys: bandwidth (no body), not server work (Express computes the full response, hits MongoDB, then hashes it to compare). Browsers revalidate like this automatically only if the response was cacheable; with no `Cache-Control`, they apply heuristics, so do not rely on it. TanStack Query (Stage 9) is the real answer for the client side.

## Stage 7 additions (verified with curl against the running backend)

New endpoint, built for 7.8 as the upload slice of B7 (`backend B7 (uploads):` commits): `POST /uploads/images`, Bearer, `multipart/form-data`, ONE file in the field `file`, JPEG/PNG/WebP decided from the first bytes, max 2 MB (`UPLOAD_MAX_BYTES`). Files are served from `GET /uploads/<name>` (outside `/api/v1`).

| Case | Request | Status | Body |
| --- | --- | --- | --- |
| Happy path | `-F file=@avatar.png` | 201 | `{"key":"<userId>-<uuid>.png","url":"http://localhost:4000/uploads/<userId>-<uuid>.png","contentType":"image/png","bytes":7875}`; `GET <url>` is `200 image/png` |
| No token | same, no header | 401 | `UNAUTHORIZED` |
| HTML renamed to `.png` with `type=image/png` | `-F "file=@evil.png;type=image/png"` | 415 | `UNSUPPORTED_FILE_TYPE` (the declared type is ignored, the bytes decide) |
| 3 MB PNG | `-F file=@big.png` | 413 | `FILE_TOO_LARGE`, "Image is too large (max 2 MB)" |
| No file / wrong field name (`photo`) | `-F note=hi` | 422 | `details: [{in:"body", path:"file", message:'Send exactly one image in the "file" field'}]` |
| JSON body instead of multipart | `-H content-type:application/json -d '{}'` | 422 | `details[0].path === "file"` |

Browser notes: do NOT set `Content-Type` on a `FormData` request (the browser adds the multipart boundary); `credentials: "include"` / `withCredentials` is needed only for the refresh cookie, the upload itself uses the Bearer token. Images load cross-origin from `:4000` on `:5173` because helmet sends `Cross-Origin-Resource-Policy: cross-origin`. `PATCH /users/me { avatarUrl }` accepts any absolute URL, so the avatar is a two-step flow: upload, then PATCH with the returned `url`.

Other contract facts the forms rely on (all re-checked this stage): `POST /auth/register` with an existing email is `409 EMAIL_TAKEN`; wrong password and unknown email are both `401 INVALID_CREDENTIALS` with the same message (no account enumeration); `POST /addresses` with a pincode that `GET /pincodes/:pincode` calls unserviceable is `422` with `details[0].path === "pincode"` ("We do not deliver to this pincode yet"); `GET /pincodes/:pincode` answers `{serviceable:false, pincode}` or the full object (two shapes, a discriminated union on `serviceable`).

## Stage 9 additions (B3, the cart; verified against the running backend)

New backend phase `backend B3:` (`GET/POST/PATCH/DELETE /cart[/items]`, `POST /cart/merge`, `POST /cart/acknowledge-prices`; details in `backend/docs/API-CONVENTIONS.md`, "Cart (B3)"). Facts the frontend relies on:

- Identity: `Authorization: Bearer` (the user's cart) OR `x-cart-token: <uuid>` (guest cart; 16-64 chars of `A-Za-z0-9_-`, generated by the client). Neither -> `400 CART_TOKEN_REQUIRED`. A bad/expired Bearer is `401`, never silently a guest. `x-cart-token` is a custom header, so the browser sends a CORS preflight; the backend's `cors()` reflects the requested headers.
- Every endpoint returns the WHOLE cart view (`items`, `saved`, `totals`, `hasIssues`), so a mutation response can be written straight into the Query cache.
- Money in the cart view is whole rupees (like products); the facade converts to paise for `computeTotals`.
- Warnings are computed on every read: `outOfStock`, `qtyReduced`, `priceChanged` + `previousPrice`. Changing a product's stock in Mongo shows up on the next GET.
- Stock: `409 INSUFFICIENT_STOCK` with `details: { availableQty, requested, inCart }` for add and for qty/move changes; a line is capped at `min(stock, 10)`.
- Merge: `POST /cart/merge { guestToken }` (Bearer): quantities add, capped; response = cart + `merge: { merged, adjusted[], skipped[] }`; the guest cart is deleted; calling it twice is safe.
- Still stubbed on the frontend (no backend yet): orders (B5) and reviews/Q&A (B7); see `features/orders/orders.api.ts` and `features/product/reviews.api.ts`.


## Stage 10 additions (B10), verified with curl and in the browser

- `POST /auth/verify-email`: `200 {message, alreadyVerified}`; unknown token `400 INVALID_TOKEN`; expired `400 TOKEN_EXPIRED`. Clicking the same link twice is a 200 with `alreadyVerified: true`.
- `POST /auth/reset-password`: `400 INVALID_TOKEN` (also for an already used link) / `400 TOKEN_EXPIRED` / `422` weak password. Success revokes every session of that user (verified: the old session's refresh is 401).
- `POST /auth/resend-verification`: `429 RESEND_COOLDOWN` with `details.retryAfterSeconds` (60 s), `409 ALREADY_VERIFIED`.
- `POST /auth/change-password`: keeps THIS session (needs the cookie) and revokes the others; `401 INVALID_CREDENTIALS` for a wrong current password (so the client must NOT treat that 401 as "token expired": `lib/api/client.ts` retries only `TOKEN_EXPIRED | INVALID_TOKEN | UNAUTHORIZED`); `409 NO_PASSWORD` for Google-only accounts.
- The user object now has `providers: ("password"|"google")[]`.
- Cookie as sent by the API in development: `refreshToken=...; Max-Age=2592000; Path=/api/v1/auth; HttpOnly; SameSite=Lax` (no `Secure` because dev runs on http: production sets `COOKIE_SECURE=true`).
- Access token payload: `{sub, role, iat, exp}`, `exp - iat = 900` s.
- Rate limiter: only login/register/verify/forgot/reset/change-password/google-start share the 30 per 15 min counter now. Refresh, logout, sessions are under the global limiter (they used to share the credentials counter, and a few tabs plus reloads exhausted it).
