# ADR 0002: Would I ship ShopSphere as an SPA or with SSR? SPA now, SSR for the product page when SEO or LCP is the goal

- **Status:** accepted (14.8). The SPA is the shipped default. The SSR build exists as an experiment (branch `stage-14-ssr-experiment`, patch in `docs/ssr-experiment/`), measured and documented, not shipped.

**Context.** The storefront was built as a client-rendered SPA (React Router in SPA mode) so the learning path could start with client-side data. Stage 13 added what an SPA can do for crawlers (prerendered static routes, per-route meta, JSON-LD after JavaScript) and Stage 14.8 asked the real question: what does `ssr: true` change, what breaks, and what does it buy? The experiment turned SSR on for the whole app, added server `loader`s for the product page and the shell, a per-request `QueryClient`, and the login form as a server `action` (details and numbers: `docs/ssr-experiment.md`).

**Decision.** Ship the SPA. Revisit SSR (for the product and category pages only, behind a CDN cache) when one of these becomes true: link previews of product URLs matter (the raw HTML of `/p/<slug>` is a generic card today), search traffic depends on pages that need rendering to be indexed, or first-visit LCP on the product page (client chain HTML -> JS -> API -> image) is the main business metric. If SSR is adopted: keep the SPA for everything behind login, put the CDN in front (the HTML of a product page does not depend on who asks), add nonce-based CSP, and decide the auth model first (below).

**What the experiment showed (measured, local machine, production builds).**
- View Source of `/p/<slug>`: 65 kB of real HTML with `<title>`, canonical, Open Graph, both JSON-LD blocks, the price and the `<h1>` (SPA: 6 kB shell, generic title, no JSON-LD). An unknown slug is a real HTTP **404** (SPA: 200 plus a "not found" screen: a soft 404).
- Lighthouse mobile, simulated throttling (median of 3): PDP 78 -> 80, LCP 6.0 -> 5.4 s. With applied throttling (real slow 4G + 4x CPU) the difference is large: PDP **56 -> 88, LCP 10.6 -> 3.7 s, FCP 9.8 -> 1.7 s**, because the product image is discoverable in the first HTML. Home and listing do not improve (LCP 8.5/9.5 -> 9.8/9.6 s): their content is client-fetched lists, and SSR without server data only moves the empty skeleton earlier. SSR pays off per route that has server data, not as a global switch.
- No duplicate fetch: the browser made 0 requests for the product the server already loaded (loader data seeds Query with `initialData` and `initialDataUpdatedAt`).
- Hydration: after fixes, 39 route/locale/preference combinations hydrate with no warning in dev (the verbose build). The defects were real and would not have been found by reading the code: an inline theme script changing `<html>` before hydration (needs `suppressHydrationWarning`), an `IntersectionObserver` check during render (server "visible", browser "not yet"), a relative "updated 9 minutes ago" text, and a locale store read at module load (the language `<select>` kept "English" after a reload because React does not patch attributes during hydration). A route with a `clientLoader` and no server `loader` is not server-rendered at all (the page body was empty for every route until the shell got a `loader`).
- The suite: 53 of 62 e2e pass unchanged. The 9 that do not are the PWA tests (no service worker build step), three production-header tests (`react-router-serve` sends no CSP/cache headers), and the SEO test that asserted "the raw HTML has no Product JSON-LD", which SSR makes false on purpose.

**Auth implications.** The refresh cookie belongs to the API origin and the access token lives in browser memory, so a server render **cannot see the session**: server-rendered HTML is always the anonymous view, and private pages (cart, orders, account) stay client-rendered skeletons. Forwarding a cookie to the API from a loader (the plan's suggestion) only works if the cookie is scoped to the frontend host, which means a backend-for-frontend design (the SSR server owns the session cookie and calls the API with it) and a different token model than ADR 0006. The login `action` demonstrates the problem: it forwards the API's `Set-Cookie` (valid: `/auth/refresh` returns 200), but the SPA's session bootstrap is gated by a localStorage hint, so the page still shows "Log in" until the client model is told. No `localStorage`, `window` or `matchMedia` may run during a server render; theme and locale live in the client and are applied after hydration.

**Other costs found.** A Node process per environment (or edge functions) with its own scaling, logs and deploys; a `QueryClient` and any store must be created per request (a module singleton would leak one user's cache into the next response); the API sees every server-side call from the server's IP (rate limiting needs `X-Forwarded-For` forwarded); a static-hosting CSP with hashes does not work when inline script contents change per request (nonces needed); the service-worker precache and the static security headers pipeline assume a built `index.html`; `.server.ts` boundaries and loader/component data flow are new concepts to maintain.

## Comparison: SPA vs React Router SSR vs TanStack Start

| Dimension | SPA (shipped) | React Router framework, `ssr: true` (experiment) | TanStack Start (the `/admin` stack) |
| --- | --- | --- | --- |
| **SEO / link previews** | Crawlers that run JS see everything; link-preview bots see a generic card (only prerendered routes have tags); soft 404s | Full HTML with tags and JSON-LD per request; real status codes | Same capability: `head()` on a route fills tags from loader data on the server; SSR by default, per-route `ssr` options |
| **TTFB** | Static file: ~1 ms, edge-cached | Server work per request (here 14 ms with a local API; in production the API round trip is added); cacheable with `Cache-Control` on the HTML | Same shape; a server function or loader runs before HTML streams |
| **First content / LCP** | After JS + API (PDP 10.6 s on slow 4G + 4x CPU) | PDP 3.7 s: HTML contains the content and the image | Same as RR SSR for routes with loader data; streaming and deferred data supported |
| **Infra / hosting** | Any static host or CDN; image is nginx (25 MB) | Node server (`react-router-serve`) or a serverless/edge adapter; health, scaling, logs, secrets on the server | Node/edge via Nitro-based adapters or Vite plugin targets; same operational weight |
| **Developer experience** | One mental model (client); Query for data; no server/client boundary | Loader/action/meta colocated per route, typed `Route.*` props, `.server` conventions, forms as `<Form>`; two runtimes to reason about, hydration rules | Fully type-safe file-based routes, search params and loader data inferred end to end; `createServerFn` gives typed RPC functions callable from components or loaders; router + Query integration is first class |
| **Data loading model** | Query in components (waterfalls possible; prefetch by hand) | Route loaders run in parallel before render; client Query still useful for interactive data; `clientLoader` available | Route `loader` (runs on server for the first request, client afterwards) + `createServerFn`; designed to compose with TanStack Query (`ensureQueryData` in loaders) |
| **Mutations / forms** | RHF + Zod + Query mutations; instant validation | `action` + `<Form>`/fetchers: works without JS, automatic revalidation; loses RHF ergonomics | Server functions as mutations (`useServerFn`), middleware for auth/validation |
| **Caching** | HTTP cache for assets and API (ETag), service worker, Query in memory | All of that plus HTML caching at the CDN (`s-maxage` / `stale-while-revalidate`); per-request QueryClient | Same options; route-level `staleTime`/`gcTime` for loader data |
| **Auth** | Token in memory, refresh cookie to the API origin (ADR 0006) | Server cannot see the session without a BFF cookie design; private pages stay client-side | Server functions run on the server and can read request cookies: a BFF-style session is the natural fit (this is the admin portal's approach to design) |
| **Complexity / risk** | Lowest; the failure modes are blank page on bad headers, stale chunks | Highest of the three for this codebase: hydration mismatches, per-request state, CSP nonces, SW/headers pipeline, split data flow | Similar to RR SSR, with a younger ecosystem and faster-moving API (check the version you pin) |

The TanStack column is from the TanStack Start/Router documentation and from reading `/admin` (a fresh scaffold: `src/router.tsx` exports `getRouter()` with `defaultPreload: "intent"`, `src/routes/__root.tsx` uses `createRootRoute({ head, shellComponent })`, and `src/routes/index.tsx` uses `createFileRoute("/")`); the admin app has no `loader` or `createServerFn` yet, so those two rows describe the documented API, not code here. Re-check against the version you install.

**Consequences.** (+) The shipped build keeps its simplicity, static hosting and the e2e suite as written. (+) The experiment gives a measured reason to move one route later. (-) Product links shared on social media show the generic card until then. (-) Soft 404s for unknown products remain (`noindex` is not set on them either; `NotFoundError` renders the branded 404 with HTTP 200). To adopt SSR for the product page only, start from `docs/ssr-experiment/` and the checklist in `docs/ssr-experiment.md`.
