# Pain journal (Stage 6, resolved in Stage 9)

Every time the hand-written data layer made me repeat myself, duplicate a request or serve stale data, it goes here. Stage 9 ticked each line off with a resolution: SOLVED, PARTLY solved or STILL painful (and why); see migration-retro.md for the summary. Format: **what hurt** (the ShopSphere moment that produced it). 22 entries, grouped.

## A. Caching and sharing between components

- [x] **No cache between pages.** Open a product from the listing and the PDP fetches `/products/:slug` although the card already held most of that data; go Back and the listing refetches page N from scratch (skeleton again). (`useProducts`, `useProduct`) **Resolution (Stage 9):** SOLVED by the shared cache + `staleTime` (2 min lists, 20 s details): back to a list <2 min old shows it instantly (9.3); hover prefetch and list-to-detail `placeholderData` make the PDP instant (9.7).
- [x] **The same product is fetched by the card and the PDP, under two shapes.** List item vs detail item are separate requests with separate schemas (`productSchema`, `productDetailSchema`), and nothing links them: no "I already have this, show it instantly and refresh in the background". **Resolution (Stage 9):** SOLVED by `findProductInCache` placeholder seeding (9.7): the card's data renders the PDP's basic fields at once; the shapes still differ (two schemas), which is honest, Query just links them at the cache level.
- [x] **Two components mounting `useFetch` for the same URL send two requests and hold two states.** Each `useFetch` call owns its own state. Header menu + filter sidebar both need the category tree: I had to hand-write a module-level promise cache in `getCategoryTree()` (and remember to clear it on failure) to avoid two requests. Worse, after a `setData` patch in one, the other still shows the old data (they cannot disagree about the wishlist ids only because I built a context for them). **Resolution (Stage 9):** SOLVED by key-based de-duplication: the category tree is ONE request/entry for 5 components (9.2); the hand-made promise cache is deleted. A `setQueryData` patch is seen by every observer.
- [x] **The same entity in many places needs a shared store I had to invent.** Heart on `ProductCard`, heart on the PDP, count in the header and the /wishlist grid all read a hand-made `WishlistContext` Set. Every other entity has no such store. **Resolution (Stage 9):** SOLVED by the `wishlistKeys.ids()` query: hearts, header count and /wishlist read the same cache entry; `WishlistContext` is deleted (9.5).
- [x] **Two sources of truth for "is it wishlisted".** `/wishlist/ids` (the Set) and `/wishlist` (the page list) are separate requests reconciled by filtering the list through the Set. Add from a card while /wishlist is open: the list does not know the new item until a reload. **Resolution (Stage 9):** PARTLY solved: both are still two requests (`ids`, `list`) but they are two entries in one cache, patched together by the optimistic mutation and re-synced by `onSettled` invalidation of `wishlistKeys.all`. Still painful: two endpoints for one fact (a server-side choice).

## B. Freshness: refetching, retry, invalidation

- [x] **No refetch on window focus or reconnect.** Leave the wishlist open, change it on another device or tab: nothing updates until I reload. The offline banner returns, but the failed rail stays failed until someone presses Retry. **Resolution (Stage 9):** SOLVED by `refetchOnWindowFocus`/`refetchOnReconnect` (on by default, throttled by `staleTime`); verified for lists and the cart (9.1, 9.6).
- [x] **No automatic retry.** A transient 502 or a dropped packet on the home rails shows the error state immediately; every retry is a button I wrote (`ErrorState onRetry`). No backoff, no "retry 3 times for network errors only". **Resolution (Stage 9):** SOLVED by `retry: shouldRetry` (2 retries with backoff for network/5xx, none for 4xx) plus a Retry button where the user must decide (9.3).
- [x] **Mutation then freshness is manual.** After `POST /addresses` I call `reload()`; after `PATCH`/`DELETE` I patch the list by hand with `setData`. Nothing says "this mutation invalidates that list". A new mutation that forgets to patch leaves a stale list. **Resolution (Stage 9):** SOLVED by `invalidateQueries(addressKeys.all)` in every address mutation's `onSuccess`; no manual `reload()` (9.4).
- [x] **Server rules copied into the client.** Deleting the default address: the backend promotes the newest address and returns `newDefaultId`; my patch code re-implements that. If the rule changes, the UI silently lies until the next refetch. **Resolution (Stage 9):** SOLVED for addresses: delete just invalidates and the server's promotion shows up; no client copy of the rule (9.4). Still copied: the cart's optimistic patches (`recount`) repeat the totals rule, rolled back/overwritten by the server response.
- [x] **Stale data on a user switch had to be handled by hand.** Signing out and in as someone else works only because the user id is in `useFetch`'s dependencies; a hook that forgets it would show the previous user's addresses. **Resolution (Stage 9):** SOLVED by `SessionCacheSync`: user-scoped query families are reset when the user changes (9.2). It must be maintained when a new user-scoped key is added (listed in one array).

## C. Mutations and optimistic updates

- [x] **Optimistic update + rollback by hand.** `toggle` changes the Set, calls the API, and on failure restores exactly one id. A naive rollback (restore a snapshot of the whole Set) would clobber changes made meanwhile; I avoided that by ignoring toggles while an id is pending, a policy a library would let me choose. **Resolution (Stage 9):** SOLVED by cache-based optimistic updates with `onMutate`/`onError`/`onSettled` (9.5): the rollback is the inverse write for that one product plus list snapshots; a policy choice, but the mechanism is Query's.
- [x] **Double-submit guard is hand-made.** A `Set` in a ref in `useAddresses` and in the wishlist provider, because state updates are async and two clicks in one tick see the same stale `pending`. **Resolution (Stage 9):** SOLVED by `mutation.isPending` and the disabled button; the synchronous guard is only a no-op check against `useMutationState` (9.4). No ref `Set` any more.
- [x] **Per-row pending/error bookkeeping.** `pending` and `rowErrors` maps in a reducer, plus the same idea again for the wishlist (`pending` Set). Each mutation hook reinvents it. **Resolution (Stage 9):** SOLVED by `useMutationState` over `variables` for per-row pending (9.4); the row's inline error is still a small `useState` in `useAddresses` (still hand-written, by choice: it is UI feedback of one screen).
- [x] **Failure UX is per-call code.** Each mutation writes its own `toast.error` and rollback; there is no one place to say "mutations show a toast on error". **Resolution (Stage 9):** SOLVED by the global `MutationCache.onError` (one toast for unexpected failures, `meta.silent` opt-out, fixed toast id) (9.4).

## D. Loading states and flashes

- [x] **Loading flash when paging or filtering.** A new filter or page is a new `useFetch` key, so the grid drops to the skeleton and back (I added `keepPrevious` to `useFetch` only for the case where I opt in; the listing does not use it, because mixing old items under new filters would be wrong without a clear "updating" signal). **Resolution (Stage 9):** SOLVED by `placeholderData: keepPreviousData` on the listing: old grid dimmed + an updating bar, no skeleton flash (9.3).
- [x] **No global "something is loading" indicator.** Each `AsyncView` shows its own skeleton; there is no top progress bar or `isFetching` count because there is no central place that knows about in-flight requests. **Resolution (Stage 9):** SOLVED by `isFetching` (`useIsFetching` is available app-wide); the listing shows its own updating bar from it. No global top bar was built (not needed).
- [x] **Per-section loading means N skeletons and layout negotiation.** The home rails each render their own skeleton; matching their height to the loaded content is manual (measured 1917px vs 2073px for the listing). **Resolution (Stage 9):** PARTLY solved: each rail is its own query with its own state (`useQuery` or `useSuspenseQuery` + boundary), 8 parallel requests (9.9). Matching skeleton height to loaded content is still manual.

## E. Pagination

- [x] **Pagination merge is hand-written.** `useInfiniteProducts` is a reducer with page tags, key tagging, dedupe by id, a busy ref and an abort controller (about 150 lines) to do what `useInfiniteQuery` does in a few options. Every race I thought of (filter change during page 3, duplicate sentinel triggers, error on page N) needed explicit code and a manual test. **Resolution (Stage 9):** SOLVED by `useInfiniteQuery` (9.8): 156-line reducer -> one options object + a 57-line adapter; races are structural (the filters are the key).
- [x] **Back button does not restore a scrolled infinite list.** Loaded pages live only in component state; a stretch would need `sessionStorage` by hand. **Resolution (Stage 9):** STILL painful: loaded pages live in the Query cache, so Back within `gcTime` re-renders all fetched pages (they are cached) but the SCROLL position is not restored, and the cache is in memory (a reload starts again). Needs scroll restoration or `persistQueryClient` (stretch, not done).

## F. Auth and plumbing

- [x] **Refresh-token rotation race.** `refreshSession()` needed a hand-written single-flight promise; React StrictMode (and a reload while a refresh was in flight, seen once with a Vite full reload) can trip the backend's reuse detection and log you out. Every client has to rediscover this. **Resolution (Stage 9):** STILL painful (and out of scope for Query): the refresh-token single-flight lives in `session.ts`; Query does not touch it. Stage 10 revisits the session; `queryClient` interacts with it through `SessionCacheSync`.
- [x] **401 handling lives in the fetch wrapper, not in the data layer.** `onUnauthorized` refreshes and retries once, but only for requests that opted in with `auth: true`; every call site has to remember the flag, and there is no queue/priority: after a refresh, all failed requests simply retry at once. **Resolution (Stage 9):** STILL painful: `onUnauthorized` stays in the fetch wrapper (`auth: true` per call). Query only decides what to do with the resulting error (`shouldRetry` never retries a 401). Stage 10.

## G. Observability

- [x] **No devtools visibility.** I cannot see which requests are in flight, cached, stale or why something refetched, except by wrapping `fetch` in the console (which is how I verified the Stage 6 behaviour). **Resolution (Stage 9):** SOLVED by the Query devtools (`ReactQueryDevtools`, dev only) and `window.queryClient` (9.1, 9.2): keys, status colours, data explorer, per-query refetch/invalidate.
- [x] **Every hook re-types its boilerplate: `useFetch` deps must be JSON-able.** `useFetch` serialises its dependencies; a Date, a function or a cyclic object in `deps` silently misbehaves, and the keys are free-form strings with no factory, so two hooks can collide by accident. **Resolution (Stage 9):** SOLVED by the key factories (`lib/queryKeys.ts`) and Query's deterministic hashing (9.2): no free-form strings, no accidental collisions.

## What `useFetch` answers

"What breaks if two components mount `useFetch` for the same URL?" Two requests go out (no de-duplication), two independent states exist (two loading flashes, possibly two different results if the data changes between responses), and a mutation that patches one with `setData` leaves the other stale. That is why the wishlist needed a context and the category tree a module-level promise.
